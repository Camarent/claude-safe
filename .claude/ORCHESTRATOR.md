# Lead as pipeline orchestrator

Read only when starting pipeline work (planning or running stages). Agents and ordinary sessions do not read this file. Owner rules apply in all projects. On-demand details live in `/root/.claude/practices/` (read the named file only when you do that action): `planning.md`, `branches.md`, `audits.md`.

## Thin mode
`/run-feature <stage>` starts `cs-wave`; the main session does not execute `orch.py next` itself; state, rounds and verdicts live in the script and `.work/<stage>/` files, agents answer in `reports/report-<id>.md`. Everything below still describes the rules the script encodes. Details, limits, what is untested: `practices/orch-pipeline.md`.

**Entry point to run a planned stage (only route):** `/run-feature <name>`, which runs `cs-wave feature --feature <name>` (Plan.md) or `cs-wave run --stage <name>` (single TASKS.md) from `/workspace` (wait, dispatch, report, headless sessions). The lead never launches stage agents by hand or loops `orch next` itself. A context clear between `next` and the agent launch leaves dispatches logged but never run: `retry` those steps, then start `cs-wave`.

**New feature or big job:** write the goal to a prompt file, then `cs-plan run --feature F --prompt-file P [--dry-run]` (the architect decides: big -> Plan.md with phases, small -> one TASKS.md; model ladder: `practices/orch-pipeline.md`; `cs-plan check`), then `/run-feature F` (runs `cs-wave feature --feature F`; `--dry-run` by hand; phase driver: plans each unplanned phase, runs it like `cs-wave run`, runs `done_when`, marks it done). Never dispatch the architect by hand for a new feature. Details: `practices/orch-pipeline.md` "Big plans". A small stage that already has a hand-written TASKS.md still uses `/run-feature`.
- Owner feedback (text, screenshots, files) is copied into `.work/<feature>/feedback/` before `cs-plan run`; the prompt file and every brief cite those paths, never the owner's original folder or "A1-A5" labels alone. Agents see only the tree.

**Driver runs in background:** start `cs-wave` (`run`, `feature`) with `run_in_background`, never in the foreground or as a detached `( ... &)`: a driver that stops on BLOCKED notifies nobody. Start it as `python3 -I -u ...` and never pipe it (`| tail` buffers: the owner's Shell details panel stays empty until exit). The panel is the owner's stage view: do not call `cs-wave status` or read the output file unless asked or the driver exits BLOCKED. Planning steps print nothing for minutes; that is normal.
**Release bump is a script step:** with `release_script` set, the planner never plans a bump/CHANGELOG/tag phase (`cs-plan check` rejects it); `version-bump` in the finish phase bumps to the `vX.Y.Z` named in the Plan.md goal. Details: `practices/planning.md` "No bump phase".
**Docs follow the pipeline:** any change to tools, steps, flags, agents or `pipeline.json` keys updates the docs that describe it (ORCHESTRATOR.md, `practices/*.md`, tool docstrings) in the same pass.
**Pipeline errors: fix the root cause.** On any BLOCKED step or pipeline error, do not stop at patching the task file and retrying: find why the pipeline allowed it (plan check, agent brief, tool, docs) and fix that in the same pass, with a test, so the same error cannot recur in any project. Then retry the step. Report both the symptom fix and the root fix.
**Wakeup fallback:** while a driver runs, also schedule `ScheduleWakeup` at 1200 s or more, so a hung driver is noticed.
**Webtest of a private artifact:** the browser is not signed in, so `web-tester` cannot open it. Test a local build served on 127.0.0.1 (the project's build and serve commands, from its TEAM.md or README); `scout` has no browser. A request that ends in a republish carries a `PUBLISH:` line, and the planner copies it into TASKS.md.
**Skip and retry notes:** `orch.py skip --step X --note "why"` and `orch.py retry --step X --note "what I changed"` take `--note`.

Local-model (Strata) steps are optional: preflight sets `STRATA=0` when it is down and they skip, see `practices/localdev.md`.
Planner and audit context step (Strata naming, digest, Haiku brief, eval, retro signals): `practices/planner-context.md`; open pipeline items: `practices/pipeline-backlog.md`.

## Role
- Sets the stage goal and done criteria; asks the architect for task files `.work/<stage>/task-N.md` + index `.work/<stage>/TASKS.md` (one concern, pattern to copy, test command, predicted paths, done criteria).
- Dispatches by file: tells an agent "take the next unfinished block from TASKS.md, mark it when done, reply in 3 lines". Never reads or retells task contents, implementation or tester/reviewer reports (if an agent returns a report in chat, save it to a file as is, no comment).
- Loop: per task `dev` -> `reviewer` (per wave, until PASS; rework per the ladder) -> per wave merge (script `merge_wave.py` in worktree mode, `merger` agent in-place) -> `final-test` (script or `tester`; `web-tester` for scripted browser checks) -> `docs-writer` -> audits -> `acceptance` (script, last phase: runs the Plan.md `## Acceptance checklist` `cmd:` lines through qrun in a fresh worktree of `stage/<feature>` (plus one per nested repo, e.g. a private course, that has that branch), removed after; writes `.work/<stage>/acceptance.md`; `eyes:` lines are listed as MANUAL, not run; FAIL stops for the lead; auditors read the file, never run it) -> `master-merged` (stage commit on `master`). `ux-reviewer` is NOT in the per-task loop: once at the end of a block, like the auditors (expensive). Release tag, tag push and `gh release create` run by the `release` script step in the last phase (owner's standing word, `practices/branches.md`; opt out with flag `no-release`): never ask the owner before them. A manual push of `master` or a tag outside that step needs the owner's word (stage-branch pushes and green-CI PR squash-merges need none).
- Lead decisions: when you change a phase's scope or outcome, update that phase's acceptance list (`Plan.md` checklist) in the same pass; an old check pinning the reversed state fails the audit. The lead also regenerates `docs/INDEX.md` in the task worktree (`cs-docs-index --root <wt>`, commit with wt.py): the dev may not.
- Rounds: Haiku first, then Sonnet, then the lead (ladder, caps and retries: `practices/orch-pipeline.md` "Rounds and fix routes"). The owner joins at block end and when stuck. "Human-only" zones (data, contracts, money, rights, publishing) live in each project's TEAM.md.
- Writes review status into the stage line of TASKS.md: `review: PASS|FAIL, round N`.
- Before block end, before `pr-ready` / the release, and before any push of `master` or a tag: sec-auditor + arch-auditor + ux-reviewer in parallel (ux-reviewer only when the block touched UI/layout, else say so). Rules and cost caps: `practices/audits.md`, read when ordering an audit; reports in files, replies <= 20 lines, lead does not read them. Audits start only after tool preflight: auditors/architects reply with TOOL-REQUESTs first, sec-auditor vets each, install, list in `/root/.claude/EXTRA-TOOLS.md`; no audit before all related tools are installed. On tools-check FAIL (orch stops, ask_main) the lead decides whether the tool can be installed at all: if yes, fix and `retry --step tools-check`; if not, mark its EXTRA-TOOLS.md row `UNAVAILABLE <date>` with a short reason, then `skip --step tools-check`.
- Planner brief = findings.md path + ctxpack slices of at most 3 code areas, <= 3k chars; never paste a long local-lead brief.
- Keeps context thin: 3-line replies, reports in files, `/compact` between stages (offer at >150k, only with no agents running), Bash through head/tail. Owner status: one sentence of progress, no agent-state lists; details only on request or when a decision is needed.
- Does not read or edit implementation, split tasks itself, run redundant agents or two agents doing the same thing. Never runs suites, coverage or mutation checks itself: dispatch `tester`/`dev`; lead reads one OK/FAIL line. If there is no Graph, ask the planner to add it.
- Planning (who plans, owner-load limit, planner split and brief template): `practices/planning.md`. Opus is for contracts, data formats, migrations and risky review marks only.

## Graph, not queue
- The planner writes `## Graph` in TASKS.md: dependencies, waves of parallel tasks (parallel only when no shared paths or generated files), and a review unit per task: `review: wave <Wn>` (one reviewer per wave; a really big task gets its own wave and reviewer). No model is written in the mark: the driver starts every reviewer on Haiku and escalates by the ccn gate or a Haiku ESCALATE, and a Sonnet reviewer stays Sonnet. Lead follows the waves, never regroups.
- After every merge and every idle moment, check the Graph and launch ALL tasks whose dependencies are merged and files do not overlap running ones. Log any skipped task with the reason in TASKS.md.
- Adding a task mid-stage (a task ESCALATEd because other work must come first): `cs-plan task --stage S --before N --title T --paths P --test CMD --done TEXT [--depends M]`. It inserts the task ahead of task-N, adds N's `depends` edge, moves N and its dependents to later waves, and runs `cs-plan check` on the result. A task counts as started when `orch.jsonl` has a dispatch or skip event for it. If no task numbered N or higher has started, the later tasks are renumbered (new = task-N). Otherwise nothing is renumbered: the new task gets the next free id, only the dependency order changes, and the command says so. When N itself has started, the new task takes the next free id and the earliest wave in which no task has started (no edge on N), and the command lists the tasks that started before it. It refuses when a started task would have to wait. Started tasks do not count against `max_tasks`. A task added to a wave after its merge step ran is merged by `merge-w<N>-late` before the next wave starts (see orch-pipeline.md, late merges); name a prerequisite task in the new task's `Depends:` line, not only in prose (`cs-plan edit-task --id N --depends M` adds it to an existing task; the plan check warns `prereq:` when a brief names a same-wave or later task it does not depend on). Cycles, unknown ids and shared paths in the new task's wave are rejected before anything is written. The counters (`tasks N/M done`, "held back") and the next `cs-wave` call read TASKS.md fresh, so the new task is dispatched first, no restart needed.
- Branches: one flow for every repo, in `practices/branches.md`.

## Models: Haiku first
- Before each launch ask: is logic written or changed? **No** -> Haiku: `dev`, `reviewer`, `tester` (runs/smoke/verification), `ops` (bulk data in the background, content-keyed cache), general-purpose Haiku for bulk data, `scout` for lookups. **Yes** (new logic, formats, guards, migrations, escaping/untrusted input, or a fix after a Haiku run found a real bug) -> the same agent with `model: sonnet` (plus `effort: medium` for `reviewer`); Sonnet = logic work, Haiku = mechanical. Never "just in case". Set `model` explicitly on every Agent call. Enforced by the PreToolUse hook `tools/model_guard.py` (matcher Agent): no `model` is denied; a non-Haiku call needs a prompt line `MODEL-REASON: <what logic is written>`; ops/scout are Haiku only. Transcription, extraction, counting, diffing are mechanical: ops on Haiku.
- Haiku with a gate (default for anything a script can judge): a gate is a command whose result decides, without opinion: a test that fails before and passes after, `scripts/dev.sh check`, a count or diff. Give the task to Haiku with the gate in the brief; gate green and reviewer PASS = done, no Sonnet. Go to Sonnet only when the gate stays red after two Haiku tries, the dev replied `ESCALATE:` after a real try, or the part is logic no command can judge (new format, guard, escaping/untrusted input, migration). A bug finding that names file:line and a failing scenario IS gateable: the brief carries the scenario as the test to write first, then the fix. No gate possible -> say so in `MODEL-REASON`. On the host pick the `pl-*` agent that fits (`pl-dev`, `pl-reviewer`, `pl-tester`, `pl-scout`, `pl-ops`); `general-purpose` only when none fits, and say why in `MODEL-REASON`. Never start on Sonnet "to be safe": the gate is the safety.
- Escalation after a failed or ESCALATE try: ladder in `practices/orch-pipeline.md` "Rounds and fix routes".
- Review per wave: ONE reviewer per wave of tasks (all merged or ready), not per task; it re-runs the mutations of every task in the wave. A task covered by the Opus architect review gets no separate Sonnet review. Dev self-checks (mutation rule, tests) stay per task. Fixes are re-reviewed at the same level.
- Code exploration goes to `scout`; the lead reads only what it will edit, and only the needed slice. Locating code (defs, refs, fuzzy "where is X") uses `lp nav|find`, see practices/code-nav.md; agents are told to.
- `effort` is set in each agent's frontmatter; override per call only deliberately. Model and effort ladder for architect and the auditors: `practices/orch-pipeline.md` "Rounds and fix routes"; what counts as risky: `practices/planning.md` "Risk and audit effort" (in the thin pipeline the planner sets it with the `flags:` line). When unsure: medium.
- Publishing: artifact pages (listening pages, reports for the owner) are built and published by the `publisher` agent (Haiku), not by the lead; give it the data files, the scratchpad dir and what the reader should check.
- Ops split: bulk data runs (transcribe, fetch, tool over many files) go to a Haiku agent in the background, filling a content-keyed cache, while the Sonnet `dev` builds/fixes the tool; check local material before network sources.

Terse output: all agents except docs-writer and publisher run in caveman voice (inlined in their agent files; `practices/orch-pipeline.md` "Caveman"). Their reports stay short but exact; briefs to them need no change.

## Briefs
- Before dispatching: `cs-brieflint <task.md>` (qrun, predicted paths, Done, file:line anchor, no tail, no absolute cd, `turns <= N`). Ops/content tasks (`owner: ops`, general-purpose agents running tools or searches) are exempt from the qrun rule; code and test tasks are not.
- Paste the exact slice: `cs-ctxpack path:START-END ...` into the brief instead of letting the agent explore/Read. Planners and auditors always get a pack. Never point an agent at CONTRACT.md/TASKS.md/PLAN.md whole (36k/31k/12k chars were Read whole once = ~20k tokens x every later turn); name the section or give a slice.
- Every test, build or check command goes through `cs-qrun -- <command>`: success prints one `OK <summary>` line, failure only the failing pieces and the log path, skipped or empty runs exit 3. No `| tail`/`| head` on tests. qrun takes ONE command; never chain `a && b` / `a; b` (last rc wins, false OK): use a script with `set -e`. If a tool's format is wrong or missing, fix qrun.py (tests in test_qrun.py), do not go back to tail.
- Review agents run only the task's test file, not the full suite (tester runs the suite once). A mutation report names the red test and shows the mutant is non-equivalent; the task test cmd must include that test (no name filter that hides it).
- Give exact tool paths (tools outside the repo, e.g. `/root/.claude/tools/docs_index.py`; a wrong path made a merge report red). docs-writer briefs list ALL the predicted files from the task file, not just `docs/`, and state the done-criteria literally (a rework round costs ~3 passes). Scout's Bash is for `lp` and read-only commands: measurement/audit tasks that run tools go to `dev`. Audit tools: `audit/audit_run.py <repo>` and `audit/audit_report.py <findings.json>`; briefs for auditors name them.
- Waiting: a background command is waited on by ending the turn (the harness re-invokes); never brief or run Monitor/sleep/poll loops or TaskStop unless asked. Ops briefs (bulk data, long runs) say so; prefer one blocking command with a timeout.
- New project bootstrap: start with the quiet wrappers from day one: tests via `qrun.py`, audits via `audit/audit_run.py` + `audit/audit_report.py` (an `audit-tools` block in AUDIT.md from the first commit), UX via `ux_shots.js`; `.audits/` in .gitignore. Never retrofit them at the end of a run.
- Sessions run as the unprivileged `node` user remapped to the host uid, so repos and files are never root-owned and no chown is needed. Root-owned leftovers from older sessions are re-owned by the entrypoint at start. Never fix "dubious ownership" with `git config --global safe.directory` (classifier blocks it).

## When stuck (review failed 2+ times, broken build, agent off course)
1. Find where it went wrong, via scout or short reads (brief imprecise? task too big? wrong agent? false premise?).
2. Break down token spend: which agent/task cost most and why (`retro/agent_cost.py`; per-task ledger: `retro/ledger.py`, see "Cost" below).
3. Fix the cause in the pipeline now (brief template, TEAM.md, agent definition, this file), then rerun at the right size.

## Lessons
- `orch.py report --text` fills only a missing/blank report file; it never overwrites an agent-written report.
Retro (thin pipeline): when `/run-feature` says `retro needed`, run `orch.py retro`, write `.work/<stage>/retro/retro.md`, fix the pipeline in the same pass; signals and numbers: `practices/orch-pipeline.md` "Retro".
Every failure, stall or repeated round yields a lesson. Name the cause in one line, then fix it where the cause lives, in the same pass, in one place only: one agent's behavior or output format -> that `agents/<name>.md`; orchestration (order, retries, what the brief embeds, gates, caps) -> driver code (`cs-wave`, `pipeline/*.py`) plus a test, a rule here only if no code can enforce it; plan or brief quality -> the architect description or the brief template in `practices/planning.md`; project facts (paths, env, data, domain quirks, owner lint rules) -> the project's CLAUDE.md, `.notes`, lint config or TEAM.md, never the shared pipeline. Prefer a script that enforces over text that asks. Never copy one lesson into several files. A lesson that names a project, path, env var or ID is a project lesson. Keep this file short: new detail goes to the matching `practices/` file, not here.

- Post-publish steps run in orch: `index-refresh` (default on, `flags: no-index` off; also a script after each wave merge, failure only warns; script `index_step.py`, no agent) and `live-check` (`UI: yes` + `PUBLISH:` line, flag `no-live` off; always `no-live` for private claude.ai artifacts: the browser cannot log in; web-tester runs `.work/<stage>/live-check.md`); FAIL -> ask_main. No hand work by lead.
- After the audits `master-merged` runs: for a pushed repo with a PR it is a script step (`pr_steps.py merge`: squash-merge once the PR is ready, mergeable and CI green, title from the `pr-title:` line of TASKS.md that the planner sets with `cs-plan stage-init --pr-title`; anything else is BLOCKED and the lead merges by hand, then `orch.py skip --step master-merged`); local repos are squashed by the `local-merge` script step and `master-merged` stays a lead pause where the lead only confirms; then `orch.py skip --step master-merged`), then `release` (last phase only; `version-bump` ran before `pr-ready`, see `practices/branches.md`), then `push-master` (ops; only for a repo with an `origin` and no PR; skipped by TASKS.md flag `no-push`) then `republish` (publisher; only with a `PUBLISH:` line) before `index-refresh`/`live-check`.
- Last step `cleanup` (ops, default on, `flags: no-clean` off): deletes the stage's finished task-*.md, leads/ and reports/report-a*.md from `.work/<stage>/`, keeps TASKS.md and orch.jsonl, so old plans do not pile up.
- `orch.py retry --step <task> --from review` reruns only the reviewer on an existing DONE dev result.

## Classifier blocks
If an agent is refused by the classifier several times in a row inside a job worktree, the lead may try those separate small edits/commands itself, one at a time (pre-authorised); the agent does the rest (tests, guards, mutations, commit). No workarounds via scripts, sed/python batches or foreign paths; if the lead is refused too, stop and tell the owner.

## Cost
Per run: `cs-agent-cost <log> --top N`. Per task, per model, with retries and cost per completed task: `cs-ledger <repo-or-logs-dir>` (run it at block end and after any stuck round; paste the 5-line summary into the stage retro).

## More lessons
- Time-based or non-isolated tests (real clock, sleep, timing threshold, a fixed shared file, folder or port) are bad design and a sign of badly separated code, not bad luck. When one flakes, do not retry, skip or loosen it: name it, and plan a task that injects the clock (a fake clock advanced by hand) and isolates the test. Only when that is impossible (rare) move it to the project's `gates_merge` (merge gate and final test only, never the task gates) and write why in the plan. The dev and architect briefs say the same.
- Before `orch.py report`, check `reports/report-<id>.md` exists. A missing file logs a false FAIL/BLOCKED. Write it from the handback, or resume the agent via SendMessage.
- Run orch only from the project root (`/workspace`). Brief agents with absolute `.work/<stage>/` paths, or a stray `<repo>/.work` copy appears.
- Release, publish and push are lead/owner steps. Never plan them as dev tasks; close the task with `orch.py skip`.
- A task made stale by an earlier plan has no diff: record the auto-dispatched rework id, then `orch.py skip`.
- Cross-task edits of one shared generated file need one owner task.
- Rebuild dist before any UX check; stale dist hides fixed bugs.
- After `retry --step audit-*` with a lead fix, orch may jump to `retro needed`; run `orch next` again after the retro, and re-run the audit by hand if orch does not.

## Warning gate
Before any merge to `master` every project check (`each` in `pipeline.json`) exits 0 with zero warnings: rule in `practices/audits.md`, project command text in the project's CLAUDE.md.
- Planning brief for `architect` (or any agent you brief by hand): first run `cs-orch leads --stage S --text "<goal>"` and paste its output into the brief. The wave does this itself for dev, reviewer, audits and fix-plan.
- Dev BLOCKED on a red full suite in a parallel wave (other tasks' half-done edits in the shared tree): do not `retry` at once, each retry is a full dev run. Wait until the wave settles, run the stage test command once yourself; if green and the task's files are in the tree, commit them and `orch.py skip` the task. Retry only when its own Done check fails.
- A repo with no `origin` is local-only: push-master reports it, never FAIL. Dev agents cannot run commands that need approval (e.g. a project validator): run those yourself or as a script step.
- Audit rounds: audits FIXES -> fix round 1 -> re-audit `-2` (sec-auditor on Sonnet, not Opus; Haiku when fixes are small) -> if still FIXES, fix round 2 -> re-audit `-3`; FIXES there goes to the lead.
- Job worktrees: with `"worktrees": true` in pipeline.json the script `tools/wt.py` creates a worktree per dev task (`.wt/<stage>/<task>/<repo>`, branch `job/<stage>-<task>`, `-2`, `-3` on a name clash, nested repos named in the task file get their own), the dev works and commits only there, the reviewer diffs the branch, `merge_wave.py` squash-merges it and runs `wt.py remove` (script merge below). Dev agents never create worktrees themselves; the old "work in place" brief applies only when the flag is off.
- Reviewer complexity gate: before a Haiku reviewer dispatch the driver (`pipeline/ccn.py`) runs `lizard` on the functions the task branch changed; any ccn above pipeline.json `review_ccn` (default 10) dispatches the reviewer on Sonnet, reason logged. Needs `"worktrees": true`; lizard missing, other languages or any error mean Haiku.

- Worktree mode, several devs / repos: one worktree set per task, distinct branch each. A task naming a nested repo gets a worktree and branch in it too. The merge covers EVERY listed repo (nested first) and only then runs `wt.py remove`. The cleanup step runs `wt.py clean --stage S` as a safety net. `lp nav|find` works inside a worktree: it builds its own self-ignored `.code-index` there.
- Script merge, commit, diff (worktree mode only): the dev ends with `wt.py commit --stage S --task T --subject "<type>(<area>): <what>"` (commits every changed worktree, nested repos too, validates the subject). The reviewer brief embeds `wt.py diff` (stat + cut diff per repo). After a wave the SCRIPT `merge_wave.py` does `wt.py merge` per task (squash, one commit per repo, reset on conflict), runs `gates` + `each`, and only on green removes the worktrees. FAIL (conflict or red tests) goes to one Sonnet `merge-fix` run of the `merger` agent (CONFLICT-RESOLVE MODE), which merges by hand in the main checkout and runs `wt.py mark-merged`, never `remove`; then the script runs again as `merge-w{N}-2`. BLOCKED (dirty main checkout, uncommitted job work) goes to the lead. No merger agent in worktree mode; in-place mode still uses it.
- Worktree structure is persisted in `.wt/<stage>/manifest.json` (`wt.py show`): task -> branch, base, root, repos. Merge, review, merge-fix and re-merge read it; `remove` drops the entry, `clean` deletes the file.
- Worktree mode has no fallback to the main checkout: `wt.py create` seeds `.code-index`, copies tracked-file mtimes, gives each worktree its OWN build dir seeded only with prebuilt artifacts (`_seed_build`; a shared build dir bakes the first checkout path into test binaries) and raises when a task names a nested path that has no git repo; the dev brief then says BLOCKED. Merge reads only the manifest. Project build facts: the project's CLAUDE.md or `.notes`.
- `test_env` in pipeline.json is an optional qrun feature; inside a job worktree it resolves to the worktree.
- Pipeline tools tests (edits under `/root/.claude/tools`, `agents/`): run `cs-ptest [PATTERN...]` (parallel, one process per file, ~20 s (22 s in the container), last line `N files, F failed, T s`). It is the entry point; never run the suite with serial `unittest discover` (minutes, gets auto-backgrounded). A single file: `python3 -I tests/test_x.py`.
