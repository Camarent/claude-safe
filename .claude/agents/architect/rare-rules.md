# architect: rarely used rules (moved from architect.md; read when the task touches one)

- Republish: when a task's Predicted paths lie inside a pipeline.json `publish` entry (its cwd, the folders its `build` command names, its page or files), the plan needs a `PUBLISH: <url>` line in TASKS.md, or `flags: no-publish` when the artifact must stay as it is. `cs-plan check` fails without one of them (in a multi-phase plan the last phase is checked, against the paths of every phase).

- UI flows: when pipeline.json sets `ux_flows` and a task adds or changes a screen, the same task updates the project's flows file (a flow that reaches the screen, with `covers` globs of the files that render it); `cs-plan check` warns `ux-flows:` for planned UI files no flow covers, and the UX audit reports an uncovered changed screen as UNVERIFIED, which becomes a fix task.

- CI parity: a task that makes a test stricter (a skip becomes a failure) or adds a tool requirement (a new linter, scanner or runtime) also updates the CI workflow files (`.github/workflows`) in the same phase. The local gates cannot see a tool that only CI lacks, so the PR check goes red after the merge. List the workflow file under Predicted paths and name the tool in `Done:`.

- Content tasks run the whole content test suite of the project (the full tests directory the content lives under, plus its tools tests), not only the new test: existing quality rules fail on new items otherwise. A task that edits existing content lines names the project's invariant tests and their exemption helpers in `Done:`; the project lists them (its CLAUDE.md or TEAM.md index may point to a planning note: read only that note, only when you plan content tasks). A project-only lesson goes into the project's own notes, never into this file.

- A tool expected to run over a minute (ASR, downloads, bulk conversion) prints a flushed progress line to stderr every N items (done/total, elapsed, estimate left); the task says so.

- Hand edits over many rows: split into id-range tasks of at most ~60 rows each, in one wave, each declaring `(rows)`; never give one model more than ~60 rows to decide (`cs-plan check` warns `size:` at 100+ rows/items/cards/...).

- Prevent big shared data files. When a plan creates new data, or a task restructures data, prefer several small separate files (per topic, unit or id range; a few hundred rows at most, or one file per record/group) over one growing file, wherever the project's loader reads a directory or glob. Small separate files let later tasks edit different files and share a wave. Do not impose it when the loader needs one file or the file is generated; then use (rows) / (mass) as above.

- Raw extractions of the owner's materials (book pages, scans, photo reads, transcripts of copyrighted text) are never tracked in git: plan them under a path that the repo ignores (the project's ignore list: `.git/info/exclude`, pipeline.json `nested_repo_excludes`), tell devs to read and write them by absolute path in the main checkout (job worktrees do not hold ignored files), and track only your own derived output (merge lists, ids, tests with synthetic fixtures). A task with such a Predicted path is wrong.

- Release, publish and push are lead/owner steps; never plan them as dev tasks. The version bump, CHANGELOG release entry and tag are done by the finish step when `release_script` is set: never plan a phase or task for them, even when the brief lists "bump to vX.Y.Z". Ignore that wording, note it in Plan.md as lead-owned, and write `release: patch|minor|major` (or the `vX.Y.Z` target in the goal) so the finish step knows the level. A final-verify task is fine only if it runs from the merged stage branch in a fresh worktree; otherwise prefer `final-test`. Never name branches or worktrees in the plan (`wt.py` creates `job/<stage>-<task>` per task and per nested repo whose path appears in the task file, so write real paths under Predicted paths).

- `UI: yes` with artifact pages published: add a `PUBLISH: <url> <url>` header line to TASKS.md (a request line starting `PUBLISH:` goes there verbatim, even without `UI: yes`) and write `.work/<stage>/live-check.md` (what to open, what must show). For private claude.ai artifact URLs add `flags: no-live` and no live-check.md. If the UX audit has `<name>` placeholders, add a `UX-VARS: name=value` line.

- `flags: docs` (the final docs step): write it only when the repo has a `docs/` folder or the TASKS.md has a `docs: <folder>` line (or `docs: skip`). A `## Docs` section in CLAUDE.md alone does not count; `cs-plan check` fails the flag without a target.

Plan.md (big feature or new project): `cs-plan plan-init`, then one `cs-plan phase` per phase (goal, `done_when` = one runnable shell command (no prose, no `|` in the Plan.md cell; chain with `&&`) or a review/test verdict, depends, owned paths; no shared paths; insert with `--after <phase>`). Phases are split into tasks later, one at a time (`cs-plan next-phase`; `--stage NN-name`). For a change to existing code skip Plan.md: `stage-init` + `task`. In `cs-plan run` you choose the route in one session: `stage-init` + tasks when you expect <= 25 tasks and no gate applies, else `plan-init` + `phase`. Every Plan.md has `## Acceptance checklist` (`plan-init` writes it empty; `cs-plan check` fails until it holds `- cmd:` / `- eyes:` lines): one line per checkable end-state item from the prompt (what must be true, not how to build it), tagged `cmd:` (runnable) or `eyes:` (auditor judges). A `cmd:` line is ONE plain shell command the driver runs after the final test from a fresh worktree of the stage branch (relative paths only; no `cd`, no `&&`, no `VAR=x` prefix, no absolute workspace path; end with an optional `(expected result)`); `cs-plan check` rejects the rest. Tasks that "decide" something (keep or drop a file, rename) get their rule as a checklist item. Content comes from the prompt and the project's notes only.

Phase size: a phase is one stage of about 15-25 tasks (hard cap 30, `max_tasks`). Order inside a phase is the stage Graph, so never cut a phase only to sequence work or separate files. Cut only at (a) an uncertainty gate: later tasks cannot be written until earlier work is merged and seen, (b) an owner step, a run on real data, or a separate repo, (c) the 30-task cap. A phase expected under about 10 tasks starts its goal with `gate: <reason>`, the reason exactly one of (a), (b), (c); "a later phase follows" is not a gate, merge it into its neighbour. Estimate tasks from the files in its paths (about 2-4 files per task) before you cut.

Owner load: a plan never hands the owner bulk work. No task may need the owner to listen to, read, label or verify more than ~10 items or ~5 minutes; hundreds of items = no gate. Automate quality control first (checks, agent sampling), then build it into the product as an in-flow action (e.g. a flag button that hides a bad clip and exports the flags). Every owner step states "Owner effort: <items, minutes>"; over the limit, replace it with a product feature or an agent check. Asking the owner is a last resort: agents decide with a sensible default, record it in the plan and go on. Ask only for owner-only zones (data, contracts, money, rights, publishing, pushing) or when two options differ in a way no agent can judge. Never schedule an owner step "just to be safe" or to confirm what an agent check or the product can verify.
