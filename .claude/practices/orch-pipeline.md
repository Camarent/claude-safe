# Thin pipeline: cs-plan run (entry) -> cs-wave (loop) + tools/orch.py; the main session does NOT run the loop, cs-wave does

Changing the pipeline code itself (tools, tests, layout, checks): read `practices/pipeline-dev.md` first; open work is in `practices/pipeline-backlog.md`.

Goal: the lead's cost is turns x context. The main Claude session is a thin executor with a flat context; a plain script
(`orch.py`, no model calls) decides everything; agents talk through files. The main session is the only one that talks to the
owner. Local model (Strata) is not part of the loop any more: agents call `lp` themselves for search and similar.

## Who does what
| part | can do | cannot do |
|---|---|---|
| main session (`/run-feature <stage>`) | run `orch next`, start the printed agents in ONE message (parallel), run `orch report --id` per agent, print start / finish / needs-main lines | decide, read files, summarize, relay agent output |
| `tools/orch.py` | Graph waves, rounds (2 failed reviews -> `ask_main`), Haiku->Sonnet escalation, request validation, budgets, prompts, verdicts from the report's first line `VERDICT: X` | judge free text (unclear = safe verdict BLOCKED/FAIL) |
| agents | as their definitions; use `lp` for code search; write `.work/<stage>/reports/report-<id>.md` (first line `VERDICT:`) and reply `REPORT <id>` | talk in chat |
| main session, outside `/run-feature` | anything else: plan, write requests (`requests/<nn>-<name>.json` + brief) for extra agents, ask the owner when `ask_main` fires | |

## Run

Map of every step and tool, from `cs-plan run` down to one task: `practices/pipeline-graph.md`.
Every job starts with the planner, never with `/run-feature`:
1. Write the request to a prompt file (goal, decisions, out of scope). Run `cs-plan run --feature F --prompt-file P [--model opus] [--dry-run]` (`--model opus` starts on Opus when the lead knows ahead that the request touches a contract, data format or migration; default Sonnet). No triage step and no model choice by code otherwise: then ONE architect session decides the size and writes the plan only through cs-plan commands (never by hand), then `cs-plan check`. Exit 2 = blocked or invalid plan: back to the lead.
   - Model: always Sonnet first (`--dry-run` is free and prints `model: sonnet`, never calls a model); no keyword or risky-file floor picks Opus.
   - ESCALATE to Opus: see "Model ladder" under "Rounds and fix routes".
   - Small route (architect expects <= 25 tasks, no gate): one stage `.work/F/` (`stage-init`, `task`). Run it: `/run-feature F`.
   - Plan-size checks (`cs-plan check --feature F`): `cs-plan phase --tasks N` stores the estimate in Plan.md; error for a phase with estimate < 10 and no valid `gate: <reason>`; error for a Plan.md with one phase (use `stage-init`); `combine:` warning (exit stays 0) for adjacent ungated phases whose estimates sum <= 25. `cs-wave feature` logs a `phase-size` metrics event (estimate, actual) after each phase is planned.
   - Big route: `.work/F/Plan.md` with phases (see "Big plans"). Run it: `/run-feature F` (`cs-wave feature --feature F`; it runs each phase as a stage).
2. The `cs-*` commands are generated shell wrappers (`tools/cmdindex.py gen-bin`, from `paths.json`): run them as `cs-wave ...`, never `python3 -I cs-wave` (a SyntaxError); to call a tool by script path use `python3 -I <tools>/wave.py`. Run them from the project root (the dir with `pipeline.json`; `/workspace` in the container), or pass `--dir`. `/run-feature <name>` is the one runner: with `Plan.md` it runs the phase driver, otherwise `cs-wave run --stage <name>` (a small stage from step 1, or a resume/re-run after a stop). Output: `Feature|Stage N started.` ... `finished: <msg>` | `needs main session: <msg>` | `error: <msg>`. Stop/resume any time: all state is `.work/<stage>/orch.jsonl` + report files.
3. Costs: `cs-ledger projects --tasks .work/<stage>/TASKS.md`.

## Files (all under `.work/<stage>/`)
Layout: top level keeps TASKS.md, orch.jsonl, metrics.jsonl, BLOCKED.md; `reports/` (report-*), `leads/` (leads-*), `audits/` (audit-*, scans.md, tools-check.md, plan-vs-changes.md), `retro/` (retro*, incidents.json); helper `util.work_path` (readers fall back to the old top-level file).
`orch.jsonl` events (dispatch/report/reject) | `reports/report-<id>.md` agent -> orch | `brief-<name>.md` + `requests/<nn>-<name>.json` anyone -> orch
(`{"agent":"researcher","model":"haiku"|null,"brief":".work/<stage>/brief-<name>.md"}`; consumed requests move to `requests/done/`).
Headless ops role may `rm` under `<project>/.work/` (cleanup step).
`run_summary.py --stage S` (the post-exit summary) prints the stage branch tip, the PR state, a `denials: dev=3 reviewer=1` line (hook denials of `tmp/denials.jsonl` counted per agent kind, most first; no line when the log is missing or no row names an agent; label and format are `DENIALS_LABEL` / `DENIALS_ITEM` in `run_summary.py`) and the last three `orch.jsonl` events.
Headless sessions get the Artifact tool only with `CLAUDE_CODE_ARTIFACT=1` and `--allowedTools Artifact` (publisher only; the PUBLISH: line is the authorization); `claude.py` sets both for the publisher only (`ARTIFACT_AGENTS`, `ENV_ARTIFACT`, `ARTIFACT_ALLOW_FLAGS` in `configuration/`).
`cs-plan edit-task --stage S --id N --field F --value V` (fields: title, paths, pattern, test, done, turns).

## When `/run-feature` stops with `needs main session`
The main session (not `/run-feature`, which only prints) acts as lead: read the named report, fix the cause itself if it can (edit, rerun a command, resolve a merge conflict), then `orch.py retry --stage S --step X --note "what I changed"` (X runs again, note in front of its prompt) or `skip --step X` (accept as is), and run `/run-feature S` again: it continues from the same place. It asks the owner only for what it cannot decide (data, contracts, money, rights, publishing).

Stage-end order (`pipeline/phases.py`): per wave merge (`merge_wave.py` script in worktree mode, `merger` agent in in-place mode), then `final-test`, `final-webtest` (flag `ui`), `final-docs`, `acceptance` (step id `ACCEPTANCE_STEP`, script, last phase with flag `test`: Plan.md `- cmd:` lines run from the stage branch in a fresh worktree, before the merge; FAIL stops the stage), then the audits once after all waves: `audit-run` script (if AUDIT.md has `audit-tools`), `sec-auditor` in parallel with `ux-reviewer` (only with the `ui` flag and a ```ux block in AUDIT.md: build/serve/url; a `ux-shots` script step (`ux_run.py`) builds, serves and screenshots first, `<name>` placeholders in the block come from a `UX-VARS: name=value` line in TASKS.md), then `arch-auditor` always, reading the sec/ux reports. Each says CLEAN | FIXES | BLOCKED. Fix and re-audit rounds: "Rounds and fix routes". A block never climbs a model ladder by itself: the wave stops, writes `.work/S/BLOCKED.md`, exits 4 and the main session decides. Infra failures stop on the first occurrence. Flags line in TASKS.md: `flags: ui docs index push merge test audit retro clean audit-low audit-high` (`audit-high` only with a `high-because: <one line>` line, else ignored).
Audit report files: auditors have no Write tool, so `orch report` copies the report to `audits/<step>.md` (via `util.work_path`) when an audit step ends CLEAN/FIXES and that file is missing; an existing file is never overwritten.

## Docs index freshness
`docs/INDEX.md` is generated by `.claude/tools/docs_index.py` (`--root .`, writes the file). Stale = the committed index differs from a fresh build: `docs_index.py --root . --fresh` exits 1 when the file is missing or differs and writes nothing. The CI step runs only when `docs/INDEX.md` is committed (this repo has none yet, so the step is omitted; see the note in `.github/workflows/ci.yml`). The docs-module-vs-index check (`docs_index.py --check`: every module needs `docs/modules/<slug>.md`) is not run by `final-docs` yet; plan check flags any Done or Test line that runs docs_index for lead verification. Note: `wt.py commit` does NOT regenerate the index; the lead regenerates it with `cs-docs-index --root <wt>` and commits with wt.py.

## Trigger log
Every Opus-class or high-effort call (the audits, `architect` with `model: opus`, any Opus request, any `effort: high`) is appended to
`.work/triggers.jsonl` with stage, step, agent, model/effort and WHY (end of base tasks; which audit said FIXES; the `high-because:`
line; the request brief). When its report arrives the outcome (CLEAN, FIXES, LANDED, MISSING, BLOCKED...) is appended. Read it with
`orch.py triggers [--stage S]`: one line each, `important=yes` when the outcome was FIXES/MISSING/BLOCKED/FAIL, `no` for a clean result, `?` while pending.
Use it at stage retro to see which high-effort or audit calls found something, and tune the "risky" criteria in `practices/planning.md`.

## Retro
- Incidents: `wt.py merge` saves each task's diff to `.work/<stage>/patches/<task>[__<repo>].patch` before the squash and the worktree removal. `orch.py retro` runs `retro/incidents.py scan` (red `final-test`, `merge-fix`, blocked `pr-ready` matched to the patches by file names in the failure text) and prints one INCIDENT line per trigger. The lead reads each, then `retro/incidents.py keep --stage S --id I --label reviewer-miss|not-a-miss|unclear --cause ".."` writes `<project>/.notes/incidents/<stage>-<id>.md`; `reviewer-miss` also keeps the patch and the task spec as a future reviewer-eval case. Project data: stays in the project's `.notes`, never in the shared pipeline.
When `/run-feature` finishes with `retro needed (...)`, the main session runs `orch.py retro --stage S`, adds the transcript numbers from `retro/ledger.py` / `retro/agent_cost.py`,
and writes `.work/S/retro/retro.md` (<= 15 lines: tripped signals with numbers, one-line cause each, the pipeline change made in the same pass). A retro is due when any of:
| signal | retro if | source |
|---|---|---|
| high effort | any call at `effort: high` | orch (`triggers.jsonl`) |
| context | lead above 150k tokens; any agent above 100k | ledger / agent_cost |
| turns | dev/reviewer/tester above 40 per call; auditors/architect above 100 (no limit on the lead's turns) | ledger / agent_cost |
| review rounds | any task with 2 failed rounds; Sonnet escalation on more than 25% of tasks | orch |
| useless escalation | a Haiku dev ESCALATE whose Sonnet run is not DONE (ESCALATE, BLOCKED, FAIL); the retro lists the chain per task (`task-5: haiku ESCALATE > sonnet ESCALATE > ...`) and finds why the upgrade did not help | orch |
| audit fixes | any FIXES from sec/arch; fix tasks above 20% of base tasks | orch |
| stuck | 3+ `ask_main` stops, or any retry/skip | orch |
| dispatches | above 30 (limit 40) | orch |
| big reads | 3+ whole-file `Read`s (no offset/limit) above 30k chars in one transcript | retro_numbers |
| explore | 10+ grep/rg calls and fewer than half as many `local.py` calls: point to explore, compare whether `local.py nav\|find` would have been faster/cheaper (code-nav.md) | retro_numbers |
| cost shape | audits+architect above 40% of weighted tokens; any task above 3x the median | ledger |
`orch.py` computes the "orch" rows itself. The "ledger / agent_cost" rows come from a last Haiku step, `ops` running `tools/retro/retro_numbers.py --orch .work/S/orch.jsonl --out .work/S/retro/retro-numbers.md` (plain script, no judgment; its failure does not stop the stage; skip with the `no-retro` flag). Tripped names from both go into the `finished:` message.
`retro/denials.py [--days N] [--projects DIR] [--examples K] [--json]` counts permission denials of headless (`sdk-cli`) Bash calls in the transcripts: total, rate, per-day rate, and denial families with count, share and an example command. No role split (role is not in the transcript).

`retro_numbers.py --out F` writes the report file and prints one line only. The file also gets per-wave sections (sessions, cost, tool table with estimated cost = session cost split by tool-call share, per-role calls) from `metrics.jsonl` (`--metrics`, default next to `--orch`). `LEAD-COST` lines (`retro/lead_cost.py`, script, USD from `pipeline/prices.py`): the lead is the interactive session (entrypoint `cli`) that runs `cs-wave`/`cs-plan`/`orch.py`, found by scanning the transcripts, and only its turns inside the stage window (first to last `t` in `orch.jsonl`) count. Per stage: the costliest leads and a total, split into cache write / cache read / fresh input / output, wall vs active time, gaps over 5 min and the extra cost of the cache rewrites after them; the `retro-digest` Haiku step copies them into `retro-digest.md`. Per feature: `feature_retro.py` adds "Lead cost of the whole feature" to `feature-problems.md` (window over all phases, one line per phase, plus the whole-transcript figure). A second project's lead running at the same time falls in the same window. Agent cost is in `metrics.jsonl`, lead cost only here. `feature_retro.py` also counts the `ask_main` stops of the feature per phase and groups them by cause (the first `RETRO_ASK_CAUSE_CHARS` characters of the message, task ids and file paths removed).
**`metrics.jsonl` fields** (`pipeline/metrics.py`). Three line kinds: `session` (one agent call), `wave` (one wave), `total` (one stage). Per field:
- `seconds`: claude wall time of the call; includes backgrounded waits, so it can exceed the API time. On `wave` and `total` lines it is the sum over sessions.
- `seconds_api`: API time only (`duration_api_ms`). Written only when the session carries it; absent in old lines. Compare with `seconds` to see the waits.
- `seconds_wall`: wave lines only, the wall clock of the whole wave (parallel sessions overlap, so it is below the sum of `seconds`).
- `cost_usd`: USD of the call (session), summed on `wave` and `total` lines. Agent cost only; lead cost is in `LEAD-COST` lines (above).
- `sid`: claude session id of the call (empty if unknown); the key to its transcript.
- `tools`: per-tool call counts, optional, absent in old lines.
- `denied`: commands the headless agent was denied (`Tool: command`, max 5), optional; a BLOCKED report names its cause here. Each entry ends with the guard name (the `rule` the hook logged in the stage's denials.jsonl for that command, e.g. `Bash: rm -rf x [reason] guard`); the name is absent when no logged row matches.
- `search`: local-search share, optional: calls of `local:find`, `local:nav-def`, `grep`, `glob`; share = local / all.
- `reason`: first line of the report, written only on BLOCKED or FAIL sessions; absent on other verdicts and in old lines.
- `LEAD-COST` is always written, one line per lead session and one total per stage or feature. When it costs $0.00 the line ends with `reason: ...` (no orch window, no lead transcript, no lead session in the window, or tiny or unpriced). The `whole session incl. N subagent log(s)` line adds the subagent logs; it is the one cost source when comparing phases.

`metrics.jsonl` session lines carry `tools` (per-tool call counts) from `claude.tool_counts()` (pipeline/claude.py); empty if the transcript is missing.
Context signals (from `context` / `context-recall` event lines in metrics.jsonl; thresholds `CTX_*` at the top of `retro_numbers.py`): `context-skipped` (no files named: Strata down, index failed, nothing matched; a skipped step is reported, never silent), `context-slow` (step over 240 s), `context-recall` (live recall under 60% with 5+ modified files). Live recall = modified files (existed before; added files cannot count) that `plan-context.md` listed, computed by `plan_context.py stage` for the audit step; files matching `context.ignore` are left out of both counts, so audio packs or caches do not read as misses. Reference-list eval: `practices/planner-context.md` "Files".
New signals: `wave-cost` (a wave above 2x median wave cost, >= 3 waves); `tools-missing` (more than half of sessions without tool data).

## Parallel waves

Wave sharing (`plan_check._overlap_problems`, `plan_files.wave_conflict`): tasks of one wave must not overlap in Predicted paths, except the same .jsonl/.tsv/.csv/.ndjson file listed `(rows)` by both. `(mass)`, unannotated and non-line-based files never share a wave; waves themselves come from `--depends` in TASKS.md. `shared:`, `size:` and `neg:` warnings never fail a check; a registry-named or data file listed by 3+ tasks is the `shared-file:` error (`errors_of`); `neg:` flags a Done/Test line whose negative grep (`! grep`, `grep -L`, `grep -vq`) searches a bare tag fragment such as `"<script"`: narrow it with an attribute or path, or a later legitimate fix is blocked by it. `Affected tests:` in a task file is a hint for the dev and reviewer briefs (`briefs.affected_note`). `tests-use:` warning (`plan_rules.check_affected_tests`, never fails a check): a code file in Predicted paths whose name is a whole word in code test files (in the repo and its nested repos) that the task neither names nor lists under `Affected tests:`; skipped for `Type: report`, test-only tasks, short names (< 4 chars) and names more than 10 tests mention; data, docs and styles are not matched.
Cite existence (`plan_check.check_cite_exists`): errors `cite-missing:` for a `path:line` cite or backticked file in a task Goal/Done/Pattern line that is neither in the tree nor a Predicted path of the task or of a task it depends on (directly or through others); a cite of an existing file whose backticked symbol is not near the cited line gives an error naming the real line.
Plan lint (`plan_lint.py`, constants in `configuration/planning.py`): errors `shared-file:` (data or registry file listed by `SHARED_MIN`+ tasks, no owner or fragments), `test-env:` (live-Chrome test reads a git-ignored path), `ux-vars:` (ui stage, ux block placeholder, no `UX-VARS:`). `errors_of` drops warning prefixes only, so `plan_phase` prints warnings and returns the errors; the architect sees them through `plan.py check`.
`next` returns every task of the first unfinished Graph wave as one `dispatches` list (`wave N: task-a, task-b`); a task with no wave is its own wave,
after the planned ones. The planner is responsible that tasks in one wave share no paths. Next wave starts when every task of the current one is PASS.
`cs-wave --dry-run` writes dispatch events.

## Guardrails (env overrides)
ORCH_MAX_DISPATCH (example value 40; unset: the task-based formula in `pipeline/limits.py` `heavy_limit`: a fixed part from the stage flags plus a per-task share, Sonnet-owned and Haiku-owned tasks weighted differently) | ORCH_MAX_OPUS=3 | ORCH_GATED=publisher (outward-facing agents need the owner via the main session).

## Running the pipeline's own tests (ptest)
`cs-ptest [--jobs N] [--dir D] [PATTERN...]`. It runs the test files in parallel and prints the slowest files and a summary line (`N files, F failed, T s`). Exit 0 means every file passes. Patterns select files by name.

## Caveman (terse output)
Only the full skill text saves tokens; a compact paragraph did not. ON for all agents except docs-writer and publisher: the skill text is inlined in the agent files between `<!-- caveman:begin/end -->` (frontmatter `skills:` does not preload here). Edit `skills/caveman/SKILL.md`, then run `python3 tools/sync_caveman.py`. To turn one agent off, delete its caveman block and remove it from `sync_caveman.py`.

Orchestrator behaviours (warnings-1 fixes):
- Usage limit: a session whose result is the short notice `You've hit your 5-hour limit · resets 8pm (UTC)` is not a failed task. `claude.session` waits until the printed reset time plus `LIMIT_MARGIN_S` (no parsable time: `LIMIT_FALLBACK_S`), then runs the same session again without using a retry; total wait per session is capped by `LIMIT_WAIT_MAX_S`, after which the notice is the result as before. A line `wave: usage limit hit ...` goes to stderr.
- Retry progress: `orch.py retry` prints one line (`REFRESH_PROGRESS` in `pipeline/cli_orch.py`) to stderr before it rebases the job branch onto the stage branch, so a slow rebase is visible; the stdout JSON is unchanged.
- No grace: `cs-wave` is the only runner and takes `.work/<stage>/wave.lock`, so a dispatch with no report at `next` means its session died: `ask_main` "never reported" at once, lead runs `retry`. `cs-wave` closes a session `REPORT_GRACE_S` (60 s) after its report has a `VERDICT:` line.
- Unclear verdict: the first missing/unclear VERDICT per task logs an `auto` retry in orch.jsonl and re-runs the agent; a second one maps to the role's safe verdict (BLOCKED/FAIL).
- Pre-approval: a line `PRE-APPROVED: master merge` in TASKS.md skips the `master-merged` pause. The driver (`phases.final_phases`) then also skips `branch-cleanup` (it exists only together with the pause) and never runs `gh pr merge`; `pr-ready` still runs. The lead merges the PR (or squashes locally) and deletes the stage branch by hand, or runs the cleanup command.

## Configuration
- `tools/pipeline/configuration/` is the single home for verdict words, role table (`ROLES`), limits, headless-session flags, environment variable names (`ENV_*`) and their defaults. Add new constants there, never as literals in other modules.
- `branch_work` defaults to `stage/{feature}`; a fixed value in pipeline.json still wins (legacy, no PR steps); `branch_release` defaults to `master`.
- Per-project values (repo folder, audit file name, `branch_work`/`branch_release`, `test_env`, `pr_checks_timeout`) live in `<workspace>/pipeline.json`; `configuration.project(dir)` overlays it on the defaults. `pr_checks_timeout` (seconds, default 1800) is how long the PR merge step waits for pending checks before it gives up (BLOCKED). A project without the file gets the defaults and autodetection. Test: `tools/tests/test_configuration.py`.

After any change to the stage sequence (`pipeline/phases.py`, a new script step, agent order): run `cs-wave run --stage S --dir D --dry-run` on a scratch project and read the printed sequence. It walks the stage on stub verdicts in a copy and prints one line per dispatch. Read it by eye; no test pins the sequence.

## lp-backed script steps
- Script steps before the audits write packed context files into `.work/<stage>/`: `audits/audit-context.md`, `audits/plan-vs-changes.md`, and `plan-context.md` for the architect. Keep them small (audit-context stops at 6000 chars).
- `prereview.py` is an opt-in gate: set `"prereview": true` in `<workspace>/pipeline.json`. After a dev DONE the local model reviews the uncommitted diff under the task's Predicted paths (a `Type: report` task or all-outside paths: the deliverable files, file mode); FAIL sends the dev back once with the reason, anything else goes to the paid reviewer.
- Shared helpers for new tools: `lpcall.py` (call lp/git, fail open), `codenames.py` (identifier and hit-line parsing, no regex), `leadparts.py` (symbols, outlines, uses), `plan_files.paths_in` (Predicted paths). Do not add another subprocess wrapper or per-language pattern.
- `usage` log: every `lp` call appends a line to `~/.claude/lp-usage.jsonl`. `find_eval.py --repo R` is an on-demand quality check, not a unit test.
- Test run: after every dev DONE the driver runs the task's `Test:` lines by script (`testrun.py`, in the task's job worktree, never the main checkout; on by default, `"testrun": false` in pipeline.json turns it off). Red -> the dev reworks with the output; red twice -> the lead; green -> pre-review / reviewer.
- Task gates (always on when the project defines `gates` or `each` and `"worktrees": true`; otherwise the dev runs the gates itself and reports a `Gates:` line): after a dev DONE and a green test run the driver runs the project's `gates` + `each` (same commands and `parallel` groups as the merge gate) once by `audit/taskgates.py` in the task's job worktree (found with `testrun.workdir`; never the main checkout; `test_env` applied). The dev brief then says to run only its own `Test:` lines and does not ask for the full set or a `Gates:` line. Unchanged worktree content (HEAD + `git diff HEAD` + untracked files, hash in `.work/<stage>/taskgates-<task>.sha`, written only by a green run) is not run again. Red -> the dev reworks with the output (no pre-review, quality run or reviewer in between): the first `GATE_FREE_ROUNDS = 2` reds are free (no dev try, counted over the whole event log); a third red goes to one Sonnet dev (a try) with all the gate outputs; a red after that -> the lead. Green -> quality run / pre-review / reviewer as before. Gates of several tasks run at the same time, each with its own `TMPDIR` (qrun); a test that writes a fixed path in the main checkout is shared by all of them. `gate_watch` (list of folders below the main checkout, default `[]` = off, e.g. `["workspace/progress"]`) makes `taskgates.py` snapshot them before and after the run (`audit/gatewatch.py`, at most `GATE_WATCH_MAX_ENTRIES` files; a bigger folder is reported as not compared, at most `GATE_WATCH_SHOW` changed paths are listed) and append a `warning:` to the gate output naming every created, removed or changed path and the test files that mention it (another job may be the cause; the warning never fails a gate). A red gate output ends with a `gate process:` block: time, cwd, the worktree's `core.hooksPath` and the variables `GATE_ENV_NAMES` (TZ, TMPDIR, HOME, PATH), `GATE_ENV_PREFIXES` (GIT_, WT_) and the names in the project's `test_env`, so an unreproducible red can be compared with a manual run. Serial gate runs are not used: they would cost the wall time of every task that waits, while a collision costs one gate re-run and a rework turn; the warning finds the shared path so the test gets fixed once.
- Quality run (advisory): after the test run is green (or after dev DONE with no test run) the driver runs `qualityrun.py` once per task: audit tools (`audit_run.py --only`, by file type: `.rs` clippy; `.js`/`.mjs` eslint, knip, jscpd, madge; only tools in the repo's `AUDIT.md`) on the files the task changed in every worktree repo, kept to changed lines. Findings -> ONE extra dev round as a recommendation (the dev may skip with a reason); clean, nothing to check, or tools unavailable -> reviewer. Never BLOCKED, never repeated. `"qualityrun": false` in pipeline.json turns it off.
- Soft scope: the task header is `Predicted paths:` (task files from before the rename are still read), the planner's expected file set, not a limit. There is no `Do not touch` field any more. The architect still plans same-wave tasks so predicted paths do not overlap, but if two devs touch the same file anyway, the merge stage resolves it. A dev may touch an extra file when the task needs it; it never fails a review for being unlisted (only a side refactor does). `wt.merge` records one `scope` line per task and repo in `metrics.jsonl` (`predicted`, `edited`, `extra` by script from the diff) for the retro to analyse; an `Extra files:` line in the report is optional. Conflicts between tasks surface at merge (Sonnet merger, then Blocked). Many conflicts = bad task split or design; fix the plan, do not re-add a hard limit.
- Plan.md without TASKS.md: `cs-wave run --stage F` on a feature folder that has Plan.md and no TASKS.md exits 4 before any guard or loop, printing ``blocked: no TASKS.md in ..., only Plan.md: run `cs-wave feature --feature F` `` (the phases are planned by `cs-wave feature`). It never prints `done: no tasks` with exit 0 there. A TASKS.md with no tasks left still ends `done: no tasks` with exit 0.
- Dirty-tree preflight: `cs-plan run`, `cs-wave run` and `cs-wave feature` refuse to start (exit 4, `blocked: uncommitted changes in <dir>: <files>`) when the main checkout holds uncommitted work, before any planning. The pipeline's own `.work/`, `.wt/`, `.audits/` do not count; nested repos are checked too. `--allow-dirty` overrides; `--dry-run` never blocks. The lead commits or drops the files first (a hung or hand-run agent may have left them).
- MAIN-DIRT attribution: `write_guard.py` logs each denied main-checkout write as `{ts, job, tool, path}` to the stage's guard log. `maincheck.read_writers` maps each path to the first job the log names for it, and `_owners` blames a changed path only on that job (or on every job when the log has no entry for it). Two jobs with overlapping changed paths: only the writer gets the MAIN-DIRT note (`test_maincheck_writer.py`).
- Red-base preflight: the same three commands run the project's gates on the base before planning when the feature or stage has no `orch.jsonl` yet (a fresh start); a red gate refuses the start (exit 4; the last line is `blocked: base is red: <first failing gate>; fix the base first`, a missing-binary failure adds a `missing binaries:` line above it). A green HEAD is marked in `.work/<name>/preflight-green.json` and not run again. No override: fix the red base first, in a stage branch and PR, then start again. `pipeline.json` `"preflight_gates": false` turns the check off.
- Nested-repo detection has one source, `worktree.nested_repos` (a git repo at most 3 levels below the repo, folders in `SKIP` such as `node_modules`, `vendor`, `.venv`, `dist` and `target` are not searched, nothing is searched inside a found repo); the plan check, job worktrees and the job-branch check all use it, so a repo outside that reach is treated as plain files everywhere.
- `ux_flows` (string, default none): path, relative to the repo root (it may sit in a nested repo below it, and may hold `<name>` placeholders filled from the stage's `UX-VARS:` line, e.g. `workspace/<course>/ux/flows.json`), of a JSON list of named UI flows `{name, actions, covers?}` (the `ux_shots.js --steps` format; each flow loads the app fresh, runs its actions, then is screenshotted and measured at phone and desktop width, light and dark; `covers` are globs of the UI source files the flow shows). The UX screenshot step passes it as `--steps` (otherwise the tool clicks the first 8 buttons and never reaches deep screens). The web-tester and the UX reviewer are told to run the flows that cover the stage's changed files; a changed UI file no flow covers is `UNVERIFIED`. `cs-plan check` fails a missing (and not planned) or invalid file and warns (`ux-flows:`) about planned UI files no flow covers. The file is project content.
- `webtest_model` (string, default `sonnet`): model of the final browser check. The check runs in batches of at most 4 UI tasks (tasks whose Predicted paths match `ui_paths`), each batch checking every `Done:` criterion of its tasks, one step per batch (`final-webtest`, `final-webtest-b2`, ...). A batch that FAILs gets one fix round; a FAIL or BLOCKED (unverified) batch is re-checked once (`...-2`) on its earlier report's FAIL and UNVERIFIED items only.
- `webtest_tools_available` (bool, default true) and `webtest_requires_tools` (list of tool-name prefixes, default `["mcp__chrome-devtools"]`): the code cannot see the tools of a headless session, so the owner says it. Set `webtest_tools_available` false where no browser MCP exists: `final-webtest` is then a script step that prints `UNVERIFIED-WEB: skipped: no browser tools ...` (report, retro digest and PR body) and does not block the stage. `webtest_requires_tools` `[]` never skips.
- `generated_marker` (regex, default `(?i)generated by|do not edit`): a tracked file whose first 5 lines match is generated. `cs-plan check` warns when one is in Predicted paths; the scope guard allows a changed generated file when a predicted source file changed.
- `webtest_build` (string, default none): a build command; when set, the `final-webtest` brief tells the web-tester to run it first on the stage branch checkout, serve only that fresh build (never an older `dist/` or similar) and name the checked-out commit (`git rev-parse --short HEAD`) in its report. Unset: brief unchanged. The command must be one the headless allowlist lets the web-tester run (pipeline.json `allow`).
- `prepare-repo` (`python3 -I pipeline/prepare_repo.py [--dir D] [--dry-run] [--add-worktrees]`) prints the list of lines it will add (file: line) before writing, only appends (never changes or reorders a line), and a second run adds nothing; `--dry-run` only prints. It adds the pipeline excludes, the `.gitignore` lines of the languages detected by marker files (`LANG_IGNORES`: `pyproject.toml`/`setup.py`/`requirements.txt`, `package.json`, `Cargo.toml`), and, when the repo has its `docs_dir` folder (default `docs`) and no `CLAUDE.md`, a git-excluded `CLAUDE.md` with a `## Docs` section (an existing or tracked `CLAUDE.md` is never edited; a `report:` line names the missing section). It only REPORTS (`report:` lines): `AUDIT.md` audit-tools lines with fewer than 4 fields (`name | cwd | command | parser`; audit-run stops on them), no `worktrees` setting in pipeline.json (`--add-worktrees` adds `"worktrees": true`; an existing value is never changed), and gate commands whose tool is not on PATH or whose `python -m pytest` interpreter cannot import pytest (put it on the driver's PATH; nothing is installed).
- `acceptance_prep` (pipeline.json list of commands, default `[]`) is the acceptance setup hook: the acceptance step runs them first in its fresh worktree (`npm ci`, a venv, a build) and a failing one fails the step, so no separate `acceptance_setup` key exists.
- `worktree_setup` (pipeline.json list of commands, default `[]`; `worktree_setup_timeout` seconds per command, default 900) is the same idea for every job worktree: `wt.py create` runs them with `sh -c` in a NEW worktree right after it is made (a reused worktree is not set up again), so a dev starts with a ready environment (venv, `npm ci`) and no task `Test:` line has to install anything. A failing or timed-out command removes the fresh worktree and stops the creation with the command and its output tail. Keep the commands idempotent and free of tests; a shared service such as a database stays in the project's check script.
- Nested repos (two keys, both off by default): `nested_repo_dir_prefix` (string, default `""` = off; set e.g. `"workspace/"`) names the dirs that are nested git repos a job worktree cannot hold: a dev task whose Predicted path names one with no nested git repo fails the plan check (only a lead step, `owner: ops`, may name one); a task whose Predicted path lies under one with no git repo stops at worktree create (a Done or Test line alone does not count). Two plan warnings help the architect (never fail a check): `open-edit:` when a task's text lets the dev edit files outside Predicted paths ("if it lives outside Predicted paths, edit it"; a nested-repo file cannot be edited from a job worktree), and `repos:` when Predicted paths lie in both the project repo and a nested repo (one task per repo). Private nested repos a task does not name are linked into its job worktree and into the acceptance worktree (`worktree.link_private`: a symlink to the main checkout's copy, so reads and project commands on a private course work; the link is kept only where git ignores a symlink of that path, so the project needs an ignore pattern such as `workspace/*` or `/workspace/name`, not `workspace/name/`); a nested repo a task names gets its own worktree. A write through a link reaches the main checkout, so a task that edits a nested repo must name its files. `nested_repo_excludes` (list of repo-relative globs, default `[]`) is written by `prepare-repo` into each nested repo's `.git/info/exclude` and `.gitignore`.
- Manual steps: a line `- ops-N manual: <what to do>` in TASKS.md, named in a Graph wave (`wave 1: ops-1 | wave 2: task-1`). The driver asks the lead before that wave and every later one runs; after the person does it, `orch.py skip --step ops-N` releases the wave.
- Extra headless permissions: `"allow": ["Bash(<cmd> *)", ...]` in `<workspace>/pipeline.json` adds `--allowedTools` entries for every session (e.g. the project's validator), so content tasks can run their Done check.
- Scratch scripts: `claude_args(scratch=...)` (driver passes the stage scratch dir) adds `Bash(python3 -I <scratch>/*)` per session, so agents run scripts they wrote there; `unzip`/`tar -x` stay denied (a `*` argument could add a second `-d`/`-C`). A project `bash_allow` replaces `BASH_ALLOW` wholesale and drops this entry too.
- `serve_commands` in `<workspace>/pipeline.json` (list of command prefixes, default `[]`): extra server commands `cs-servectl start -- <command>` may run, e.g. `["npm run serve"]`. Only the loopback static server `python3 -m http.server --bind 127.0.0.1 <port>` is allowed without it. A prefix ending in `<port>` takes exactly one port number. No shell: `;`, `&`, `|`, `$(`, backticks, `>`, `<`, newlines and `sh -c`/`bash -c` are refused. Checked by `pipeline/serve_rule.py` in both `servectl.py` and `cmd_guard.py`.
- Failure classifier and escalation gate (2026-11-03): a red task test run is classified by `pipeline/classify.py` (`code` | `plan` | `infra` | `unknown`; qrun exit 3 splits on whether the `Test:` path matches a file or a Predicted path creates it); `plan`, `infra` and `unknown` go to the lead on the first occurrence, never up a model ladder. Before the first paid step of the dev ladder (the Sonnet dev) the script `localmodel/escalation_gate.py` shows the local judge (thinking on) the whole task brief, the stage's `plan-notes.md`, the project repo's `AGENTS.md` (missing files are skipped), the last 3 failure reports (only the newest is the live failure; older ones are 600-char context) and asks: can the dev finish with the brief and repo as they are? PASS when the brief, notes, rules or a repo file settle the question, or it is a defect, a stale report or a weak model. FAIL (veto, the task goes to the lead) only for a fact no file supplies, an owner-only choice no rule settles, or a blocker outside editing; the quoted line must come from the newest report. The answer may carry `kind` (`plan_error` = the brief contradicts a test or itself: the lead edits the task; `missing_fact`, `owner_choice`, `environment`), stored in gate.jsonl and shown in the ask message. No quote or no answer = the ladder goes on (one-way veto, fails open). Replay past cases with `localmodel/replay_gate.py CASES.json` (same builder and judge, no log; see `replay_cases.example.json`). Off with `"gate": false` in `pipeline.json`. Every call is appended to `.work/<stage>/gate.jsonl` (judge verdict, reason, quoted line, seconds, failure files, thinking flag); `retro_numbers.py` prints `gate_lines`: calls, vetoes and what the lead did next (retry, retry then PASS = possible false veto, skip, open), go-ons and whether Sonnet then fixed the task.
- Review loop: after a reviewer FAIL the dev reworks; when the job branch HEAD (every repo) is unchanged since that reviewer's dispatch, the rework added no commit and the driver asks the lead (`rework added no commit since reviewer FAIL <id>`) instead of paying for a second review of the same code. The HEAD is logged as `head` on the reviewer dispatch event.
- Judge the pre-review gate by the retro line: local FAIL then paid reviewer PASS = wasted rework, local pass then reviewer FAIL = missed by the gate.
- Mutation check timeout (`pipeline/configuration/limits.py` `MUTATION_GATE_TIMEOUT_S`, 300 s): the reviewer session carries `PIPELINE_GATE_KIND=mutation` (`ENV_GATE_KIND`), and qrun kills each gate run in it after this limit instead of `GATE_TIMEOUT_S`. The full gate and dev sessions keep `GATE_TIMEOUT_S`. Both stay under the agent tool timeout; `ORCH_SCRIPT_TIMEOUT` still caps them.
- Session cwd: a dev session runs in its job worktree root (`driver.session_cwd`, with `worktrees` on); reviewer and read-only roles run in the project dir.
- `gates` in `<workspace>/pipeline.json` is the only way to configure the final test (the old `full_test` string is rejected with a config error). Without `gates` and `gates_merge` the Haiku tester runs and `merge_wave.py` reports that nothing was run. `each` adds per-folder checks: `{"glob": "<pattern>", "cmd": "<command with {dir}>"}`. The dev runs the gates once before DONE, and `final-test` becomes the script `final_check.py` (runs every command through qrun, no model). The web-tester is unchanged.
- `gates` is a list of `{"name": "<id>", "cmd": "<shell command>"}` that mirrors the project's CI (one gate per CI command, e.g. `lint`, `test`). Each `cmd` runs as one `sh -c`. Names must be unique and `cmd` non-empty, else a config error. `final_check.py` and `merge_wave.py` run each gate separately, in order, and stop at the first red one: the FAIL report says `gate <name>: FAILED` with the output tail, so the merge-fix dev and the fix round see which gate failed.
- Opt-in parallel gates: a gate may carry `"parallel": "<group>"`; gates with the same group run concurrently (group runs at its first member's position, results stay in config order, a red gate stops later units). The group name is the safety contract: never group gates that share a build dir or write the same files.
- Merge-only gates: `gates_merge` in `pipeline.json` is a list with the same entries as `gates` (`name`, `cmd`, optional `parallel`; names unique across both lists). It runs only at the merge gate (`merge_wave.py`), the final test (`final_check.py`) and the red-base preflight (the base must pass what the merge gate runs), never in `taskgates.py` and never named in the dev brief. The merge gate runs once per wave merge, so a slow `gates_merge` command runs after every wave. A red one goes to the merge fix step like any red merge gate. Its commands are checked at plan time (`pipeline.json gates_merge `<name>``), counted by the CI drift warning and the toolchain check, and logged in `gate_cmd` records with `kind: merge`. Use it for the rare test that cannot be made fast and isolated (real time, a shared file); a time-based or non-isolated test is bad design and a sign of code that is not separated: first inject the clock (a fake clock advanced by hand) and isolate it. Example: `"gates_merge": [{"name": "premerge", "cmd": "npm run test:premerge"}]`.
- Final-only gates: `gates_final` in `pipeline.json` (same entry format) runs in the final test only (`final_check.py`), once per stage: never in a task's gates, at a wave merge or in the red-base preflight. Use it for heavy real-data tests that `gates_merge` would repeat at every wave merge. A gate name is unique across `gates`, `gates_merge` and `gates_final`. A base-red clearing never applies to it (the preflight does not run it), so a gate that is red on the base fails every final test until fixed. `cs-plan check`, the CI drift check and the toolchain check read it like the others.
- `cs-qrun --postgres -- <cmd>` starts a scratch Postgres for one command: `pipeline.json` `qrun_pg_start` (list of strings, required) runs in a fresh instance dir (env `QRUN_PG_DIR`) and prints the URL as its last stdout line; the URL goes to the command env as `qrun_pg_var` (string, required, e.g. `DATABASE_URL`). When the command ends (also on timeout or SIGTERM) qrun kills what the start command started and removes the instance dir. A missing or failing key is exit 2 and the command does not run.
- `registry_files` (list, default none): `[{"path": "<repo-relative file>", "when": "<regex>"}]`. A task whose file text matches `when` (case-insensitive) must list `path` in its Predicted paths, or `cs-plan check` fails. A registry file that many tasks append to (a validator-code array, an id list) was edited by tasks that did not list it, so the overlap rule never put them in separate waves and the merge conflicted. Listing it makes them sequential. The project writes the rules; the pipeline has no built-in registry names.
- CI drift warning: when `.github/workflows/*.yml` exist, `cs-plan check` and the `tools-check` step list every CI `run:` command that no gate covers (a gate or an `&&` part of one; `npm ci`, `npm install` and `echo` lines are skipped; so are lines whose first word is in the default list `CI_DRIFT_DEFAULT_IGNORE` in `configuration/pr_gates.py`: install, download, unpack, mkdir, exit). The workflow folder is looked up in the project's `repo` folder. Without gates the warning is "no gates configured; CI drift not checked". It never fails a check. `"ci_drift": false` turns it off. Each drift warning and each red CI-only line in pr-ready ends with the `ci_drift_ignore` entry to add (the line's leading words, printed exactly); add that entry to `pipeline.json` to name a CI-only command. Lines that need a GitHub-only variable, a secret or a bare shell setting are never run locally and never drift. The cite check runs after green Test lines; `"cite_check": false` in `pipeline.json` turns it off (default on).
- `scans` in `<workspace>/pipeline.json` (list of command strings, no shell, 600 s each): the script step `scans` (`scans.py`) runs before the audits and writes `.work/<S>/audits/scans.md`; the sec/arch auditors read it instead of running gitleaks, cargo audit and the like. Findings still give DONE; a command that cannot start gives BLOCKED. Not set: nothing changes.

## Rounds and fix routes
- Per task, `pipeline/steps.py` `next_step`: Haiku dev -> (opt-in pre-review before every paid review; its FAIL = a dev rework that costs one try) -> reviewer; on dev ESCALATE, red test run or review FAIL a retry that carries the failing report (`Rework: fix the findings in <file>`), Haiku first, then Sonnet dev, then the lead (the local advice step was removed 2026-11-17; an old `"advice"` key in pipeline.json is ignored); a `Type: report` task (see planning.md) has no quality run and no model route of its own; its pre-review runs in file mode (`prereview.py` judges all Predicted text files in ONE call with `lp judgefiles`; input over `PREREVIEW_INPUT_TOKENS` (40k est. tokens for now, `est_tokens`; ceiling 103762 = the 128k window minus answer, prompt and 15% safety; raise after timing real inputs) = SKIPPED, never chunked; the model lists up to 20 findings, each must quote a shown line or is dropped; diff mode is the same: ONE `lp review` call, whole diff; stamped `diff-sha` = hash of the files): dev -> test run -> pre-review -> reviewer on Haiku, like any task; the reviewer moves to Sonnet only by E1(c) (its own ESCALATE), where it then stays. `MAX_TRIES = 4` (per task: at most 4 runs of the dev and 4 of the reviewer, any model, then the lead) and `MAX_ROUNDS = 2` in `pipeline/configuration/`.
- Model ladder (the one home; other docs point here; the rule "Haiku with a gate" is in ORCHESTRATOR.md "Models: Haiku first"): `dev` and `reviewer` start on Haiku. Escalation rules (numbered; the driver is `steps.py` `next_step`, tested by `test_escalation_ladder.py`, wording checked by `test_escalation_docs.py`):
  1. E1: a dev or reviewer step moves from Haiku to Sonnet only after one of these four events, and no other: (a) the gate command stayed red after two Haiku tries; (b) the dev reply is `ESCALATE:` and names one concrete reason; (c) the reviewer verdict is `ESCALATE` and names one defect with file and line; (d) a merge-gate fix dev (fix-gate) ended BLOCKED, or its re-merge FAILed, so the next fix is a Sonnet dev.
  2. E2: a reviewer verdict is exactly one of `PASS`, `FAIL`, `ESCALATE`. `PASS` means wrong, risky and nit counts are all 0. `ESCALATE` with all three counts 0 is invalid: the driver treats it as `PASS` and logs a warning with the report id.
  3. E3: a file path pattern never selects a model. Do not add routing by path, topic or word such as "network" or "parser".
  4. E4: an escalation runs once per task and step. After it the next verdict is final for that round; a second `ESCALATE` of the same kind blocks to the lead with the named reason.
  Every Sonnet dev or reviewer dispatch logs its why `E1(a)`, `E1(b)`, `E1(c)` or `E1(d)` (`pipeline/e1.py` `model_for`); a task with no E1 event runs on Haiku. Sticky: after an E1(b) dev dispatch the task's dev stays on Sonnet; after E1(c) the reviewer stays on Sonnet.
  The first dev ESCALATE with its reason (E1(b)) goes to the Sonnet dev with the escalate report as rework; the local judge gate reads it first. A second ESCALATE blocks to the lead (E4). A dev ESCALATE naming a plan gap goes straight to the Sonnet dev, no judge gate: `ESCALATE: PLAN GAP: <what is missing, file:line>` (the plan lacks something the task needs; from Sonnet it goes to the lead with the text) and a FIRST dev run that ESCALATEs with zero edits (job worktree with no commit and no uncommitted file; `steps.straight_to_sonnet`); a Sonnet failure goes to the lead. `PLAN GAP` matches with `:`, `-`, `–` or `—` and an optional `VERDICT:` prefix (`steps.PLAN_GAP_RE`). A lead `orch.py retry` after a dev ESCALATE (last dev report before the marker) starts the dev on Sonnet, why `retry by lead after ESCALATE: Sonnet`; after a reviewer FAIL, a dev BLOCKED or an auto retry it starts on Haiku as before. The plan never marks models. `architect` runs Sonnet, Opus only after its `VERDICT: ESCALATE` (contract, data format, schema, migration, save/progress or scheduling change: it writes `.work/F/ESCALATE.md` with why, files and facts found, decisions made and what is open; `cs-plan run` re-runs planning once on Opus, which reads that file first, `plan_run.run`). `arch-auditor` and `sec-auditor` (owner 2026-11-08) start on Sonnet; Opus with `audit-high`, or once after their own `VERDICT: ESCALATE` (first pass only; step `audit-sec-opus`, same report file, turn cap `auditor_escalate_max_turns` default 80 vs `auditor_max_turns` 40; tables `AUDITOR_ESCALATE` / `AUDITOR_START_MODEL` in configuration); re-audits cheaper. Effort for these three is chosen per call: default `medium`, `low` for a small diff, `high` only per "Risk and audit effort" in `practices/planning.md`.
- Stage checks, `pipeline/phases.py`: `final-test` and `final-webtest` get ONE fix round: FAIL -> `fix_step` (architect adds fix tasks with a later `wave K:` line; it replies BLOCKED when the tool or environment failed, not the change) -> the normal waves run them (dev, reviewer, merge) -> the check re-runs once (`-2`); a second red result goes to the lead (`ask_main`). Each audit that said FIXES gets TWO rounds (`audit_phases`): fix round 1, re-audit `-2` (sec-auditor on Sonnet, Haiku when the fixes are small), then if still FIXES fix round 2 and re-audit `-3`; FIXES from `-3` goes to the lead. Order: tests, browser check, docs, audits, so the audits see the code with the fix tasks.
- A re-run does not repeat earlier checks: after a web-test fix round only the web-test re-runs (each task already ran the gates before its DONE).

## Big plans (Plan.md with phases)
- Each phase is a stage (`.work/<feature>/phases/NN-name/`) with its own TASKS.md, waves and docs. `cs-plan stage-init` gives every phase except the last the flags `no-audit no-push no-index no-live no-clean`: the phases only merge their tasks into the work branch (`stage/<feature>`). PR steps (`pr-open`, `pr-push-w<N>`) are feature-level and are not disabled by `no-push` on middle phases. The closing `NN-finish` phase carries the audits (their `master..stage/<feature>` diff covers every phase), `pr-ready`, the master-merge pause, `branch-cleanup`, push, publish, index, live check and cleanup, so those run once for the whole feature. Put `PUBLISH:` / `PRE-APPROVED:` lines only in the last phase.
- Entry: `cs-plan run --feature F --prompt-file P` (the architect's `big` route writes Plan.md), then the phase driver below. Do not start phases by hand with `cs-wave run --stage F/phases/NN-name`; use that only to resume one phase.
- Phase driver: `cs-wave feature --feature F [--dry-run]` runs the open phases in dependency order: plans a phase with one architect session when its TASKS.md is missing (so it sees what earlier phases built), runs the stage like `cs-wave run`, runs the phase's `done_when`, runs `cs-plan phase-done`. It stops with exit 4 (back to the lead) on a planning problem, a stage that asks the lead (the `NN-finish` phase ends with the master-merge pause), or a failed `done_when`; exit 3 on a stage limit. Re-running resumes. Audits: the last phase always; a middle phase once `audit_every_tasks` (pipeline.json, default 25) tasks piled up since the last audited phase (`pipeline/phase_audit.py`). pipeline.json `sec_audit_paths` (fnmatch list, unset = always): the sec audit runs only when the stage diff touches a matching path. `ops_scripts` (list of `cleanup`, `push-master`, `retro-digest`; unset = the ops session) runs those steps by `ops_steps.py`, no model. `preflight_denied` (list of command prefixes) makes `cs-plan check` flag a Test line that starts with one. `merge_fix_conflict_only` (default off): a merge FAIL without a git conflict goes to the lead, not the merger.
- Status line: `cs-wave run` / `feature` print one line per batch, e.g. `[p2/3 02-api] wave 2/2 · tasks 1/5 done · dev×2 · 7 model calls · $0.40` (`pipeline/progress.py`); stage-end steps show their id instead of a wave.
- Headless Bash: `sed -n 'A,Bp' file` is allowed (`SED_PRINT_ALLOW`; cmd_guard `sed_why` denies a `sed -n` with extra options or any script but the print range, also behind `snip run --`; other sed forms stay outside the default allowlist). Dev and reviewer sessions get `--add-dir` for `SCRATCH_ADD_DIR` (`/tmp`, roles in `SCRATCH_ADD_AGENTS`) so scratch reads outside the worktree work; that directory is shared by every job and the permission covers edits too, while the qrun `TMPDIR` of a gate stays private. Only the read-only roles also get the project root.
- Plan check `docs`: the `docs` flag with no docs target (a `docs:` line in TASKS.md or PROGRESS.md, or a `## Docs` section in the workspace CLAUDE.md) is an error, because `final-docs` would end BLOCKED.
- Stage size: at most 30 tasks per stage that have not started (`max_tasks` in `<workspace>/pipeline.json`; tasks with a dispatch or skip event do not count, so the lead can add a fix task to a running phase without editing pipeline.json). `cs-plan check` rejects more ("split into phases or two stages") and the runner asks the lead if a hand-written TASKS.md exceeds it; fix tasks added by a fix round (after a `fix-plan` report) come on top. Bigger work goes into a Plan.md with phases, each phase its own stage.
- Task output paths: `cs-plan check` (`check_work_paths`) rejects a relative `.work/` path in `Predicted paths:` or `Done:` ("use the absolute main-tree path /workspace/.work/<stage>/..."). A scout or dev runs in a job worktree that is deleted afterwards, so a relative output is lost. An absolute `<workspace>/.work/` output is exempt from `check_git_paths` (it is scratch, not git-tracked); no commit is needed for it (`wt.commit` skips a clean tree).
- Republish (`PUBLISH:` URLs): a URL with a `publish` entry in `<workspace>/pipeline.json` gets its recipe in the brief (`build` in `cwd` with `{out}` = the stage scratch dir, then `page` and `files` published in place); a URL without one fails when its page cannot be built.
- Fewer returns to the lead: a failed wave merge (script or `merger`) gets one Sonnet `merger` fix in CONFLICT-RESOLVE MODE (`merge-fix-wN`) and a second merge (`merge-wN-2`) before the lead is asked; the partial merge of a wave with a stuck task (`merge-wN-pK`) takes the same route with suffixed steps (`merge-fix-wN-pK`, `merge-wN-pK-2`; a red gate there still asks the lead); a failed `index-refresh` or `cleanup` is only a warning; a step that was running when `cs-wave` stopped (dispatch without a report) is re-run once automatically at the next start, then it is the lead's call; `tools-check` fails only for tools the project's AUDIT.md names (`xtools.py --needed-by`); the ops role may answer FAIL. Still the lead's: a task stuck after the Sonnet rounds, a check red after its one fix round, the architect's BLOCKED, push / republish / live-check failures, red CI (`pr-ready` BLOCKED), `deps-sweep` notices, the master-merge pause (skip it with `PRE-APPROVED: master merge`).
- Sonnet/Opus limit formula (`pipeline/limits.py`, used when `--max-dispatches` is not given): fixed part (2 audits, 1 audit-fix architect, 2 re-audits, 1 test-fix architect; +1 UX audit and +1 web-test fix architect for UI) + 4 per Sonnet-owned task + 2 per Haiku task; recomputed from TASKS.md before every batch, so fix tasks add their share. A safety net against runaway loops, not a budget. Tune with `heavy_per_sonnet_task` / `heavy_per_haiku_task` in pipeline.json.
- Limits (`cs-wave`; exit 3 at a limit, a rerun starts the counters again): anchored to the task list; only heavy sessions (Sonnet and Opus: the dispatch's model, else the agent file's default) count, Haiku sessions and script steps are free. `--max-dispatches` (default: the formula above; also used for lead requests `orch.py request` and the retro "dispatches" signal at 75%; `ORCH_MAX_DISPATCH` overrides it), `--max-waves` (default off: a heavy wave holds at least one heavy dispatch, so the dispatch limit already bounds it; when set, counts waves with a heavy session), `--max-sessions` (loop guard over all model sessions, default 60 + 8 per task), `--max-budget-usd` (cost), `max_tasks` 30 per stage. The status line shows `N Sonnet/Opus calls`.

- Agents and the lead commit through `tools/commit.py --subject "type(area): what" [--body T] [--dir D]` (validates subject, appends the trailer from `commit_trailer` in pipeline.json); nobody writes the trailer or subject check by hand. It never stages.
- Late merges (worktree mode): when every task of a wave is done, a task of that wave whose job branch the wave's merge step never took (added to the wave, or retried, after `merge-w<N>` ran) is merged by a script step `merge-w<N>-late` BEFORE the next wave starts, so no later task branches from a base that lacks a done task's commit. Each late dispatch records the tasks it covers (`tasks` in its orch.jsonl event). A task that finishes (or is retried and finishes again) after a late batch gets a batch of its own, `merge-w<N>-late2`, `-late3`, ...; a batch whose ladder is still running (script FAIL, merger fix, re-merge) continues under its own ids; a task that is still unmerged after its batch goes to the lead (ask_main). `orch.py retry --step merge-w<N>-late<k>` resets that batch's fix ladder. The plan check warns (`prereq:`, never an error) when a task file names another task of the same or a later wave that it does not depend on: add the dependency with `cs-plan edit-task --id N --depends M`: it moves the task (and what depends on it) to the wave after M, refuses a cycle or a started task that would have to move, prints what changed, and notes when the stage thereby enters dependency mode (a stuck task no longer stops the stage). The dependency lives in TASKS.md (the graph), not in the task file; the plan check reads only the graph. `orch.py retry` prints a `warn` when the task file or note names another task (`task-N`) whose finished work is not merged yet (add it to `Depends:` so it is held until merged, or merge it now), and `wave.py status` lists the done-but-unmerged tasks.
- Red merge gate and stale branches: `merge_wave.py` merges first, then runs the gates. On a red gate it removes the worktree and branch of every task whose content is already on the stage branch (the fix goes on the stage branch; a leftover would make the driver say "unmerged" and block). `graph._unmerged_done` also treats a done task as settled, and removes its worktree, when its content is on the stage branch (`worktree.settled_job`: empty, `is_merged` or a valid `wt.py mark-merged`), so a hand merge needs no `wt.py remove --force`.
- Gates red on the base: a task-gate run (`taskgates.py`) that is red runs its red commands once more on the stage base (the main checkout at the stage branch). A command red there too is not counted against the task; the report names it (`red on the stage base too`). `"gate_base_check": false` in pipeline.json turns it off. It matches by command, not by failure text. Nothing is cleared when the main checkout is dirty or off the stage branch, for a command the base does not have (an `each` folder the task added), or for exit 124/127 (timeout, cannot run).
- Red on the base at the merge gate: a red merge gate or final test counts against the stage. The red base is never recorded or cleared, because the preflight refuses to start on it. Only the per-task base check (`gate_base_check`, task gates) clears a red that the stage base has too.
- `NO FIX`: a dev that finds no edit by any model can help (an upstream package with no fixed version) replies `BLOCKED: NO FIX: <why>` (`ESCALATE: NO FIX:` works too). The driver asks the owner once ("NO FIX, owner decision") and runs no ladder; `orch.py retry` after the cause is fixed, or `skip` (`steps.NO_FIX_RE`).
- `Type: webtest` tasks (steps.py `_next_webtest`): the web-tester agent (Haiku) runs the task, PASS then runs the task's `Test:` lines by script on the stage branch checkout (`testrun.workdir`), DONE ends the task. FAIL/BLOCKED of the web-tester or a red Test goes to the lead once.
- servectl accepts `--directory <folder>` for the loopback static server when the folder is inside the workspace (symlinks followed); `/` or another project is refused (`serve_rule._outside_workspace`).
- Merging a task branch by hand: run `wt.py merge --stage S --task T` (squash, branch subject) or `merge_wave.py --tasks T`; never `git merge --no-edit job/...`: its generated message names a job, the commit guard refuses it and leaves the merge staged (backlog 89).
- `cs-wave` and `orch.py` print `lead context high: Nk tokens, ...` to stderr past 150k tokens (`pipeline/lead_context.py`; source: usage of the last turn in the newest session log under `projects/`, silent if missing); hand off and start the next phase fresh.

## Tools layout
`/root/.claude/tools/` keeps the entry points at the top level (`wave.py`, `plan.py`, `orch.py`, `qrun.py`, `wt.py`, `pr_steps.py`, ...). Helper tools live in packages: `audit/` (audit_*, scans, qualityrun, final_check), `retro/` (feature_retro, retro_numbers, incidents, ledger, agent_cost), `search/` (local, localq, codesrv, strata, ask_code, ctxpack, lsp, lpcall, leadparts), plus `pipeline/` and `localmodel/`. Each moved tool keeps a thin shim at its old path (`tools/<name>.py` runs `tools/<group>/<name>.py`), so agent files, briefs, `lp` and permission allowlists keep working. Python imports use the new names (`from audit.audit_run import ...`); `tests/test_entry_shims.py` covers the shims. Tests stay flat in `tests/`.
- Task with no change: `taskgates.py` does not run the gates when every repo of the job worktree is still at its base commit with nothing changed (a read-only audit: its output is outside the repo). The gates would repeat the base's result and load the machine for minutes; the merge gate still runs the real code. When a red gate is not cleared against the stage base, the report says why (`not cleared against the stage base: ...`: main checkout dirty or on another branch, command not on the base, exit 124/127, or green on the base so the failure is the task's or a collision with another task's gate run).
- Nested repos a task does not list: its job worktree only links them (a write through the link reaches the shared main repo). When a dev starts, the dev brief takes a snapshot of the linked main repos (`pipeline/linkguard.py`, `.wt/<stage>/<task>/linkbase.json`): the first one keeps the tracked and untracked state for the job's life, a later attempt only moves the recorded HEAD up (another task's merge is not the dev's commit); `wt.py remove` deletes it. After the dev, `testrun.py` and `taskgates.py` compare: a tracked file changed since then is saved as `.work/<stage>/linkwrite-<task>-<stamp>-<repo>.patch` and reverted; new untracked files and a commit in the main copy are only reported (never deleted: a test of another task may use them). The task goes back to the dev as a red run, not to the lead. What was already there at the start (a lead's edit) is not the dev's. Tasks that run at the same time share the main copy, so another task's write after the snapshot is blamed on this one (its patch is kept); a lead's edit made between two attempts is blamed the same way; an untracked file is compared by name only; a repo git cannot answer for at the snapshot is not guarded until the next one. The dev either reports `pre-existing red` and finishes, or runs `wt.py add-repo --stage S --task T --repo workspace/<course>`, which swaps the link for a real worktree on the job branch and records it, so commit, review and merge cover it. Planned edits still belong in Predicted paths.
- Gate timing metric: `metrics.jsonl` gets one `gate_cmd` record per gate command run by the task gates (`kind: task`, with `task`) or a wave merge (`kind: merge`, `task` = the merged ids): `gate` name, `rc`, `seconds`, and `base_red: true` when the command was red on the stage base too (its `rc` is then 0). Read it for per-gate timings instead of scraping report text.
- Public-words baseline: `public_words_baseline` in pipeline.json (default `docs/public-words-baseline.txt`) names the file of accepted hits. A hit key is `file TAB word TAB line text stripped` (no line number, stable when lines move); `public_words.read_baseline` and `public_words.diff` read and compare it. Blank and `#` lines are ignored; a missing file is an empty baseline. Generator: `.claude/tools/public_words_baseline.py` with `--write` (rewrite the file, sorted, deduped), `--dry-run` (count the lines it would change, write nothing), `--check` (exit 1 on a hit not in the baseline), `--words a,b` (override the configured words).
- Public-words gate: on a public repo, a hit whose key is not in the baseline fails the gate; the output prints `file:line: word` and `add to <baseline>: <key line>` per new hit. A baseline entry with no hit prints `stale: <key>` and does not fail.
