# Auditor rules (all projects; read when ordering an audit)

- Auditors and architects use tools for everything a tool can do (tools as much as possible, manual work only where no tool exists; a repeatable manual check becomes a tool request or a small script). Auditors never judge by eye: they first run the stack's tools (size, complexity, duplication, dead code, dependency graph, `cargo audit`/`npm audit`/secret scanner, licences). Norms per language: `/root/.claude/practices/<stack>.md` (rust, rust-wasm, js; new stacks are added as they appear, with sources and thresholds). Each project has `AUDIT.md` at the root: its tools and exact commands, threshold overrides, exclusions, allowed licences. No `AUDIT.md`: create it first (architect/dev, from practices), then call the auditors.
- Modes: `diff <range>` (default at block end) and `full` (whole tree; mandatory before the first public release, every few blocks, and when files grow). After the first `full`, audits run as `delta <prev-sha>..HEAD`, where prev-sha is the last release squash on `master` (a job branch's squashed sha is gone); ranges are `master..stage/<feature>`: tools over the whole tree, judgement only on changes, closed findings marked. The lead's brief names the mode and the report path `.work/<stage>/audits/audit-arch.md` / `audit-sec.md`; it switches to `full` rarely (old report or big diff).
- The full report always goes to a file; the auditor replies to the lead with a summary of <= 20 lines. The lead does not read or retell it: the arch report holds a REFACTORING PLAN, the lead passes its path to architect, who cuts it into small tasks (file extractions before features).
- Extra tools: every tool installed beyond the container image is listed in `/root/.claude/EXTRA-TOOLS.md` (Accepted / Recommended for permanent install / Rejected, each with install command, version, licence, network use). Preflight: before an audit or architect pass, the auditor/architect first checks that every tool named in `AUDIT.md` and the practices is installed and replies with `TOOL-REQUEST: <tool> - <why> - <install command> - <licence/cost>` lines only, running NO audit. The lead then sends the requests to `sec-auditor` (need + safety: organisation/maintainer, activity, popularity, licence, telemetry, runtime network, install scripts). ACCEPT: dev/tester installs it outside the project tree and adds it to Accepted; if it is common and useful for every project it also goes under Recommended for permanent install and the lead proposes baking it into the image to the owner (the owner decides). REJECT: add it under Rejected with the explanation, do not install. Only after every related tool is installed (or rejected, with the audit then marked incomplete for that area) is the audit started.
- Tool rules: prefer free/open-source without account or telemetry; paid or account-bound only as a last resort and after asking the owner. Only common tools from official registries/releases; record the version in `AUDIT.md`; nothing is added to the project's packages; unknown or obscure tools are rejected. `TOOL-MISSING: <tool>` found mid-audit means the preflight failed: stop, route it like a TOOL-REQUEST, rerun the pass after the install; an audit with a missing tool counts as incomplete.
- Planning: architect read practices and `AUDIT.md`, do not grow files past the threshold (a split task comes first), add no dependency without justification.
- Audit history (repo level, outside the stage): reports live per commit in `<repo>/.audits/<date>-<sha>-arch|sec.md` + index `.audits/LATEST.md` (local, gitignored; the owner may decide to commit arch reports). The stage-level reports of a run are `.work/<stage>/audits/audit-arch.md` / `audit-sec.md` (see Modes). Findings have stable IDs and a status still-open/fixed/changed.
- Suppression review (owner rule, 2026-11-06): arch-auditor and sec-auditor list EVERY suppression added in the audited range (`#[allow]`, `#![allow]`, `eslint-disable`, `noqa`, tool ignore/skip/exclude lists, raised thresholds, cargo-machete/deny ignores, coverage excludes; `git diff <range>` on added lines) in a "Suppressions" section: file:line, the rule, the reason given, who added it (task/role), and a verdict AVOIDABLE or JUSTIFIED. Every AVOIDABLE one is a FIXES finding that asks for the real fix, not a bigger allow; a JUSTIFIED one needs a narrow scope and a written reason on the line. A suppression without a verdict fails the audit.
- Commit messages, squash into the stage branch and into `master`: `practices/branches.md`.
- Test coverage: every project's `AUDIT.md` has a "Coverage" section (tools, exact commands, exclusions, baseline numbers at a commit); norms and tools: `/root/.claude/practices/coverage.md`. The arch audit measures coverage (overall, per module, changed lines in delta) and compares with the baseline in `.audits/LATEST.md`; tester at stage end checks that coverage of the touched files did not drop. Percent is a signal, not a goal; critical seams (scheduler, migrations, parsers) must be covered; the baseline in `AUDIT.md` is refreshed after each audit.
- Before the first release into `master`: commit messages name no jobs and every date is +0000 (rewrite under `TZ=UTC`); hooks do not enforce this yet.
- The secret scanner (gitleaks) must be installed; hooks only warn when it is missing, so check it before the scan.
- Quiet audit run: auditors first run `cs-audit <repo> [--baseline <prev findings.json>] [--base <ref>]` (tool list = the `audit-tools` block in `AUDIT.md`; whole tree; `--base` (the stage base ref; the pipeline passes it) also lists the lint suppressions added in BASE...HEAD; raw logs in `<repo>/.audits/raw/`; a `--only <tools>` run writes `<stamp>-only-<tools>.json` there, never the consolidated `*-findings.json` the auditors read), then read only its stdout and `cs-audit-report <findings.json> [--top N] [--tool X] [--group file|rule]`; open a raw log only for one specific finding. Exit 2 (`TOOL-MISSING`) = incomplete audit; exit 3 = nothing ran.
- Efficiency rule: every milestone auditor (arch-auditor performance, sec-auditor efficiency, ux-reviewer render/interaction efficiency) reports an Efficiency section: measured vs suspected.

## Audit cost rules
1. Before any audit/ux run a Haiku `ops` agent rebuilds the dist from the exact commit and fails loudly if the build does not finish; the ux brief names that dist.
2. ux-reviewer full pass on Sonnet once; every re-check passes `model: haiku` and a turn cap of 30.
3. Re-checks only after ALL fix rounds of the block are merged, one combined re-check, never per round.
4. The lead orders fix rounds only after every audit of the pass has reported.
5. Auditors/web-tester briefs: turn cap (<=60), ctxpack first, one finding list file; 90+ turn runs get split.
- Warning gate (the one home of the rule): before any merge to `master`, every check the project lists under `each` in `pipeline.json` (a validator, a linter) exits 0 with zero warnings. A warning is never left "for nothing": either the check is wrong (fix or extend it, with a test) or the content is wrong (fix the content). No blanket ignore. Enforced by the `final-test` step; whenever a stage touches a check or the content it checks, the planner adds the check update as a task. Project command text: the project's CLAUDE.md.
- A green test count with skips hides failures: reviewers check the skipped count. A gate that falls back to synthetic data and stays green is a silent skip; make "gate did not run" loud.
- Reviewer runs its own mutation and rejects tests that only grep source or call internals by hand.
- Does a test inject a dependency that production never provides (a false green)? Name the production code path that supplies it.
- ux-reviewer and web-tester rebuild dist first and check index.html is newer than the HEAD commit; a stale dist gives false defects.
- Empty range: a `diff`/`delta` audit whose range has no changed files audits nothing (e.g. the stage branch equals `master` after a history rewrite). Use `full` then, and always `full` for a feature that rewrites history or packages a repo for release.
- Acceptance checklist: when the plan has `## Acceptance checklist`, the audit brief names that file, and each auditor reports every item as PASS/FAIL/UNKNOWN with file:line evidence, before its own findings. The checklist content is project-specific; the tools and auditor agents stay generic.
- Opus sec audit is conditional by default: it runs only when the diff base..work branch touches a security-relevant path (`configuration.SEC_AUDIT_PATHS`, case-insensitive: auth, secrets, tokens, shell, http, guards, settings, json, lock, js/ts, git files, env files, Dockerfile, CI; words net/url/path/cmd/exec only as a basename word), adds a line matching `SEC_AUDIT_CONTENT` in a code file (not docs or tests), or deletes any line of a non-test code file (pure renames do not). `sec_audit_paths` in `pipeline.json` replaces the path list (fnmatch); `["*"]` restores the old always-run. An unreadable or empty diff keeps the audit.
