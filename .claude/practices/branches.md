# Branches and merging: read when branching, merging or sending the merger

- One flow for every repo: only `master` is long-lived. Each stage or feature gets a short-lived branch `stage/<feature>` cut from `master`; job branches squash into it; tests and audits run on it. A fixed `branch_work` in `pipeline.json` still wins (old projects).
- Job worktrees are created by the script `wt.py` (branch `job/<stage>-<task>`, cut from `stage/<feature>`); dev agents never create worktrees, and the lead does not create or merge them by hand.
- Job branches merge into the stage branch by `git merge --squash`, one commit with a proper message. Worktree mode: the script `merge_wave.py` merges, runs gates and `each`, deletes branch (`git branch -D`, squash does not mark it merged) and worktree; on conflict or red tests it resets and reports FAIL, and one Sonnet `merger` run (`merge-fix-w<N>`, CONFLICT-RESOLVE MODE) investigates, fixes and finishes the merge (generated files are regenerated, not hand-merged), then the script runs again. In-place mode (no worktrees): the Haiku `merger` agent does the merge; on `CONFLICT` it aborts and reports, on red tests (`MERGED-TESTS-RED`) it changes nothing and reports, then the Sonnet fix run follows.
- Delete the branch and worktree right after the merge.
- Do not merge or delete a job branch while rework (-r2, nit fix) runs on it: wait and merge once, or merge first and start the rework with `--base stage/<feature>`. Exclude branches with live agents before merging.
- Stacked branches: squash-merge the top branch as one commit, then move each later branch with `git rebase --onto stage/<feature> <old-base-sha>` (the sha the branch was cut from, verify it first).
- Local-only repos use the same flow, just without the PR: no `origin`, no push, the lead squash-merges locally.
- Job/branch/report names never reuse an existing task number: check existing names first.
- Release = squash-merge of the stage branch into `master`, one commit per stage, never `--ff-only` and no merge commits. Only after the full suite, both auditors and ux-reviewer (if UI changed) on `master..stage/<feature>`. Pushed repo: the PR is opened as a draft after plan check, the branch is pushed after each wave merge (never force), and the lead squash-merges the PR on GitHub when CI is green (`gh pr merge N --squash --delete-branch`, no owner confirm needed). Then `git fetch --prune origin`, fast-forward local `master`, delete the local stage branch. Red CI: stop and report. Local repo: the script step `local-merge` does `git switch master`, `git merge --squash stage/<feature>` and commits (subject from `.work/<feature>/SUBJECT` line 1, else `chore(<feature>): squash stage branch <branch>`); the lead only confirms and skips `master-merged`. `branch-cleanup` deletes the branch.
- Commit messages: `<type>(<area>): <what was done>` (feat/fix/refactor/test/docs/chore), no job names, dates +0000 (`TZ=UTC`). A job branch enters the stage branch as one squash commit; the stage-to-`master` squash commit (stage title + bullet list) and a GitHub PR squash (`gh pr merge --squash --subject ... --body-file ...`) use the same message. A GitHub-made squash is not checked by the local hook: pass subject and body explicitly, then check the commit after the merge. History is not rewritten routinely.
- Dev and merge briefs: commit with `-F msgfile`; dev agents leave changes uncommitted unless the brief says to commit.
- Push: `git -c credential.helper='!gh auth git-credential' push` of explicit refs. Stage branches and PR merges need no confirm; pushing `master` directly, tags and releases need the owner's word.
- Release tags `vX.Y.Z`: the pipeline cuts one per feature, in the last phase only (owner's standing word, 2026-11-03), through the project's `release_script` (pipeline.json, repo-relative; `current [REF]` and `set OLD NEW ENTRY`; without it no release steps run). Script step `version-bump` before `pr-ready` (patch unless TASKS.md says `release: minor|major`, the owner's call at planning; commit `chore(release): vX.Y.Z`), then `release` after `master-merged` (tag the merged PR's squash SHA, push the tag, `gh release create`; local-only repo: tag only). Opt out with flag `no-release`. A manual tag or release outside this needs the owner's word.
- Dependabot (pushed repos): the `deps-sweep` script step runs before the stage branch is cut. It squash-merges open Dependabot PRs whose checks are all green, leaves red or pending ones open and lists them, then runs `git fetch --prune origin` and fast-forwards `master`. Opt out with `"deps_sweep": false` in `pipeline.json`.
- Nested repos (own local git inside the main repo): the driver creates the same `stage/<feature>` branch in each nested repo, job worktrees of that repo are cut from it, `branch-cleanup` runs per repo and refuses unmerged work, and `local-merge` squashes each nested repo into its release branch. PR, `pr-ready` and `deps-sweep` steps stay main-repo only; a nested repo is treated as local-only even when it has an `origin`.
- New local repo: set the owner's git identity right after `git init` (a merger cannot commit without it); project hooks and identity text: the project's CLAUDE.md or `.notes`.

## In-place mode only (the `merger` agent merges; worktree mode uses `merge_wave.py`)
- Merger commit message: write the full message (with the trailer) to a file yourself and tell the merger to `git commit -F` it unchanged; briefs that only name the trailer get overridden by the attribution reminder. The merger is a dumb tool: the brief gives the target branch, it judges nothing.
- The merger brief must say to commit the worktree changes before the squash, else it finds "nothing to squash". A test command in the brief must not end in a stray `.` (discover treats it as a path and runs 0 tests).
