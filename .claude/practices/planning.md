# Planning: read when ordering a plan

Plan rules the architect acts on (owner load, phase size, criteria first, task-file format, no model marks) live in `agents/architect.md`; entry route (`cs-plan run`, `cs-wave feature`) in ORCHESTRATOR.md. This file holds what the lead needs.

- Who plans: big block of several stages = ONE `architect` call for the whole block (plan + task files). Small stage, bug pack, screenshot fixes = `architect` too. Model ladder and ESCALATE: `practices/orch-pipeline.md`; the lead does not escalate to Opus on its own.
- Planner split: big plans go in 2 passes (outline + TASKS.md graph, then task files), first file written by turn 25 (planner 20); check with `retro/agent_cost.py` after the run.
- Release in a brief: say only the level (`release: minor`) or the target `vX.Y.Z` in the goal. Never list "bump version / CHANGELOG / tag" as work: the finish step does it (see "No bump phase").
- Planner brief template (hand briefs): Goal / Decisions already made / Context pack (ctxpack `path:START-END`, plus the warning/count lists when relevant) / Out of scope / Output files / turn cap / "run brieflint on task files". Write it to `.work/<stage>/brief-*.md` with the findings file path and send "reply in 3 lines". Planners and auditors always get a pack; prose only makes them spend ~50 tool calls finding code.
- Dev and reviewer briefs: "no new lint/clippy allow without a reason line; the reviewer flags it". `audit/audit_run.py <repo> --base <ref>` lists the suppressions added in `<ref>...HEAD` as findings (tool `suppression`).
- Dev brief for new Python files: list the owner's lint rules: E402 (no assignment between `sys.path.insert` and imports: inline the expression), E731 (no lambda assignment), SIM117 (combine nested `with`), PLW1510 (`subprocess.run` needs explicit `check=`), RUF100 (no unused noqa), I001 (import order per the owner's config).
- Group risk review: one call over a set of related tasks, default `architect` on Sonnet (ladder: `practices/orch-pipeline.md`).
- After a lead fix use `skip` or `retry --from review` (Haiku reviewer), never a full dev `retry`. When all work sits in place on `stage/<feature>` (no job branches), `skip` the merger step.
- Task test lists must include tests that assert retired or removed sets; only the merge run catches those. Parallel branches adding JS files can break sibling tests that hard-code script lists: say so in the brief.
- In-place mode: merge agents tick only their own task line in TASKS.md; the merger's reply is its report.

## Changing a plan while it runs
Do not widen a task by hand when it needs other work first. Insert a task ahead of it: `cs-plan task --stage S --before N ...` (details in ORCHESTRATOR.md "Graph, not queue"). Tasks that are done or in flight keep their ids and waves; the new task then gets the next free id and task-N waits for it by a `depends` edge. Keep the new task small: `cs-plan check` runs on the result (size cap, predicted-path overlap).

## Risk and audit effort (defines "risky"; read by planners, used by `orch.py` flags)
The planner writes one `flags:` line in TASKS.md (`ui docs no-merge no-test no-audit no-publish audit-low audit-high`) from the whole stage, not per task:
- **High** (`audit-high` + a `high-because: <one line naming the category and the file/format>` line) when the stage touches any of: (1) data that cannot be recovered: migrations, deletes, rewrites of stored or user data, changed data/file formats; (2) a public contract other code or users depend on: API, CLI, schema, wire/file format, ids; (3) auth, secrets, permissions, money, personal data; (4) outward-facing or history-changing steps: publishing, push, history rewrite, deploy config.
- **Low** (`audit-low`) when the whole stage is small (about <= 5 files and <= 150 changed lines) AND touches none of the four categories above: docs, tests-only, copy, layout, mechanical or pattern-copy edits.
- **Medium** (no flag) for everything else, and whenever unsure.
- A request line starting `PUBLISH:` (artifact URLs to republish): copy it verbatim into TASKS.md as a header line, unchanged, and write no other `PUBLISH:` line. The driver's republish step reads only TASKS.md; `cs-plan check` fails when the request has the line and TASKS.md lacks it.
- Exec of a config-supplied path (`subprocess`, shell, spawn): the task file states the trust boundary (who writes the config) and the allowed-path rule (root, no `..`, no symlink escape, no shell string), with a C<n> test for a path outside it.
- Spec vs existing gates: before writing tasks, run the full suite and the strict validators on the base (record failures that already exist on it) and list the gates and tests the change must touch (insert-only checks, N-only tests, `--strict` modes); put each exception in the task spec (file, gate, new expected behaviour) so a dev does not find it when the suite goes red.
- A rule that must match existing data ("X only on Y"): before fixing the rule text, the plan counts violations against current data (a C<n> in Done criteria with its proving command, e.g. `grep -c`/script) and decides the exception-list shape (file, key, owner) in the task.
The lead may override the line before `/run-feature`; `audit-high` without `high-because:` is ignored by `orch.py`.
- Task size and gates (`cs-plan check`): above 25 predicted files = error: split by seam (no warning below that; every task starts on Haiku). A file covered by a protected gate (pipeline.json `protected_gates` [{name, paths}] or `protected gate <name>: <globs>` in AUDIT.md) must be named with its gate in the task text, else a `gate:` warning. Errors: a Predicted path that is untracked or ignored by the repo (brieflint, run by `cs-plan check`), a `Test:` with `grep -c`, a `jq` key missing from the named file, a `done_when` file nobody produces. A file listed by 3+ tasks = `shared:` warning (never fails): shared registry files (i18n catalogs, schemas, snapshots, lockfiles, generated files, index lists) get ONE owner task that adds all the phase's keys/entries up front (later tasks read the file and do not list it; touching it for an unplanned key is soft scope), or each task gets its own new per-feature file the registry loads. Same Predicted file in one wave stays an error; order tasks by real code dependencies only. `no-release` in some phases only: `release:` warning (the driver reads the flag from the final phase).
- Row-level sharing (`cs-plan check`): in `Predicted paths:` a line-based data file (.jsonl, .tsv, .csv, .ndjson) may carry `(rows)` (the task edits only the rows or id ranges its text names) or `(mass)` (it changes most or all rows). Two tasks may share a wave on a file only if it is line-based and both say `(rows)`; git merges disjoint line edits. `(mass)` and unannotated entries (whole file, the old rule) never share: make one depend on the other. A mass edit of a file is its own task for one dev. The `shared:` warning is silent for a file whose sharers are all `(rows)`.
- Registry files: an append-only registry/list many tasks add ids to (EDITED_IDS array, ids.lock) is not edited by tasks; each task adds its own fragment file (`tests/<registry>/<task-id>.js|json`) read by the registry's glob, and the first task that needs it makes it glob-based. `shared-file:` error for 3+ tasks on one file named like ids, lock, registry, edited or list (a line-based data file may have one owner with the rest `(rows)`).
- Affected tests: tests that probably assert the old behaviour the task changes (search the tests); list them if you find any. `none` is valid. A design conflict goes to the lead as `ESCALATE-PLAN: <conflict>` at planning time.
- Open decisions first: before any task file, the architect lists every open decision a task depends on (a brief rule that conflicts with an existing test invariant; a strict-validator gate against a marker removal; a lock file that covers only some item kinds; missing data such as glosses). Each is settled in `plan-notes.md` from existing rules (AGENTS.md, CONTRACT.md, project notes) or returned to the lead with `ESCALATE-PLAN:` BEFORE any task file exists. A task never carries a "lead must decide" path.
- Done counts and external data: a count in `Done:` comes from the guard's own checker (validator or test run at plan time), never from an audit estimate. A criterion that needs external data names its source file and the command that produced the number.
- Test ban (`cs-plan check`): pipeline.json `test_ban` = list of `{pattern, use}`; a `Test:` command part (wrapper words stripped) matching a pattern is a `testban:` error naming the `use` text. A malformed entry is ignored, never an error.
- Shell operators after `cs-qrun --` (`cs-plan check`): cs-qrun runs a program, not a shell, so `cs-qrun -- ! grep ...` or `cs-qrun -- && ls` exits 127. A `Test:` line with `!`, `&&`, `||`, `|` or `;` as the first word after `cs-qrun --` is a `qrun-op:` error: wrap the shell part as `cs-qrun -- bash -c '...'`.
- Errors of `cs-plan check` (each message says the fix): `shared-file:` = a data file (.jsonl/.ndjson/.tsv/.csv) or a registry-named file (whole name token ids, lock, registry, edited, list; test files excluded) listed by 3 or more tasks (`SHARED_MIN`) unless it is a directory or glob entry (fragments), or every listing is `(rows)`; one owner = all listings but one are `(rows)` (then only the `shared:` warning). `test-env:` = a `Test:`/`Done:` command needing live Chrome (chrome, chromium, puppeteer, playwright, --remote-debugging, headless) whose named test file reads a path that `git check-ignore` reports ignored: use a synthetic fixture. `ux-vars:` = flag `ui`, a `<name>` placeholder in the AUDIT.md ```ux block and no `UX-VARS: name=value` line in TASKS.md naming it.
- Task sizing: a hand edit over many rows is split into id-range tasks of at most ~60 rows each, one wave, each `(rows)`. `size:` warning (never fails) when a non-script, non-report task names 100+ rows, items, cards, prompts, answers, findings, sentences, ids, entries or questions.
- Prevent big shared data files. When a plan creates new data, or a task restructures data, prefer several small separate files (per topic, unit or id range; a few hundred rows at most, or one file per record/group) over one growing file, wherever the project's loader reads a directory or glob. Small separate files let later tasks edit different files and share a wave. Do not impose it when the loader needs one file or the file is generated; then use (rows) / (mass) as above.
- Regex: unsafe, may match several places; rule lives in `agents/dev|reviewer|architect.md`.

## Task type, inputs and report tasks (`cs-plan check`)
- Header `Type: code|report` in a task file (default `code`; any other value is a plan error). A `report` task delivers a list/report file (usually under `<workspace>/.work/<feature>/...`), not a repo diff: the driver runs dev -> test run -> local pre-review in file mode (the Predicted text files md/txt/tsv/csv/json/jsonl are judged against `Done:` in ONE local call; over the token budget `PREREVIEW_INPUT_TOKENS` = skipped, never chunked or cut) -> reviewer, with no quality run, and the reviewer is on Sonnet from the first review.
- Validator rule: a `report` task whose `Test:` is only an existence check (`test -s`, `test -f`, `[ -s ... ]`, `ls`) fails `cs-plan check`. The architect writes a small validator script (`python3 -I` or `node`: row counts, required columns, totals add up) as part of the task; its exit code is the gate. List it in `Test:` and `Predicted paths:`.
- `Inputs:` header (optional; lines or comma separated): files the task needs, relative to the workspace or absolute, or `tool:<name>` (on PATH or a script of the repo). `cs-plan check` fails when one is missing, naming task and input. An output of an earlier task of the same stage is written `after:task-N:<path>` and is not checked (it does not exist yet).
- Research task (`Type: research`, same field as `Kind: research`): one tracked `Outputs:` path (a git-ignored or work-folder path fails); a later task that depends on it names the path in `Inputs:` (`after:task-N:<path>`). Scout on Haiku writes nothing; the driver commits the file. Use it for a document that collects facts from several tasks, not for a final-docs step.
- An `Inputs:` path that nobody produces needs an `ops-N` manual row the task depends on (its text names the path); `cs-plan check` fails otherwise. The driver blocks once up front, before any dispatch, and lists the open ops steps.

## Per-file tasks and tools over data (`cs-plan check`, `cs-plan dryrun`)
- Decide per file: a task whose Goal/Done says "for each file decide ..." (phrases in configuration `PER_FILE_PHRASES`) needs a per-file acceptance beyond the checklist: an `Outputs:` line (one expected file or count per input), or a `Test:` that fails while a file is undecided (it holds a phrase of `PER_FILE_CHECK_PHRASES`, e.g. `undecided`, `for f in`). Else `cs-plan check` fails.
- Tool over data: a task with a `Tool:` line, or a script in Predicted paths used with `--dry-run`/`--dry`/`--check`/`--preview`, needs `Dry run: <cmd>  # expect > N changes`. `cs-plan check` fails without it. `cs-plan dryrun --stage S` runs each such line in a throwaway detached worktree of the repo HEAD (checkout and `.work` untouched, worktree removed), reads the first `<n> changes|updated|records|files...` count of the output and exits 2 when it is not above N, or the command fails. Opt-in: tasks without the line are not run. The worktree holds committed files only, so for a tool the task itself creates, make the command a probe of the data (a `grep`/`jq` that prints the count of records the tool will change). Run it before `cs-plan run` hands the plan to the devs.
- Ignored Predicted path (`cs-plan check`): a `Predicted paths:` entry that is ignored by git (existing or not yet created, in the repo or a nested repo) is a problem line naming the path: the dev cannot commit it. Drop it or plan it outside the repo.

## No bump phase
When `pipeline.json` has `release_script`, never plan a phase or task for the version bump, CHANGELOG release entry or tag: `cs-plan check` rejects it. The finish step `version-bump` does it. Name the release in the Plan.md goal as `vX.Y.Z` (first 12 lines): that version is the bump target (`pr_ops._goal_version`); a version already at the goal gets no second bump. Without it the level (`release: patch|minor|major`) applies. Push, tag and republish stay behind the owner's word.

## UI and design jobs (grounded process)
A plan that adds a screen or a UI flow follows this template, in this order. Each step is a task or a named ops step; a later step never starts before the earlier one is signed off.

1. Entity glossary first: one table of entity, API route and screen per entity. Read the entities from `docs/ARCHITECTURE.md` and `docs/modules/` (the task-1 glossary). A screen with no entity or route is not planned.
2. Owner sign-off ops step on the glossary, before any screen is designed.
3. Journeys before screens: each user journey is written as steps over the glossary entities.
4. Screen inventory: per screen the data source, the controls and the exits. Check it with `python3 -I .claude/tools/ui_inventory_check.py`; a failing check blocks the task.
5. One connected prototype on shared domain sample data: every screen of the inventory is reachable from the others, and all screens read the same sample data.
6. Rendered review against the inventory: reuse the flows in `.claude/tools/pipeline/ux_flows.py` to walk the rendered prototype and compare each screen with its inventory row.
7. Owner sign-off gates: the phase does not close until the owner signs off the rendered review.

Phase gate: a UI phase that has no owner step or real-data run is not done. Its gate reason reads exactly: `gate: owner step or real-data run`.

## Pinning tests and docs counts (`cs-plan check`)
- Pinning tests (`pins:`): a task that edits a data or setting file a test pins (a `configuration` folder, a data file, or a .py word list) must list that test in `Test:` or `Predicted paths:`. Else `cs-plan check` fails. Reason: the dev runs only the listed tests.
- Docs counts (`docs-count:`): a docs task must describe the behaviour, not write machine counts or line numbers into a hand-written doc. Those belong to the generated `docs/INDEX.md`, which no task writes by hand. Reason: a hand-written count goes stale at the next change.

## Acceptance checklist
Plan.md `## Acceptance checklist`: one `- cmd: <one shell command> (expected result)` or `- eyes: <item>` line per end-state item. `cs-plan check` rejects a line with another tag, and a cmd with `cd`, `&&`, an env prefix or an absolute main-checkout path. After the final test the `acceptance` step runs each cmd through qrun from a fresh worktree of the stage branch (removed after, stage branch and main checkout untouched), writes `.work/<stage>/acceptance.md` and lists `eyes:` lines as MANUAL for the lead. A failed cmd stops before `master-merged`. Auditors read the file and never run it.

## Carried from earlier phases
A phase after the first starts from what the earlier phases left, not from the goal alone. Its TASKS.md has a `## Carried from earlier phases` section: each item carried from the earlier reports (FAIL, DEVIATION, DOCS-STALE lines), audits (FIXES still open) and earlier tasks is either a task of this phase or a `- not needed: reason` line. A DEVIATION (a file changed outside its predicted paths) is either owned by a task here or named as accepted. `cs-plan check` fails a later phase without the section, or with a bullet that is neither.

- Guard before data fix: a task that adds a validator warning or error (strict gate) must not merge before the task that fixes existing data. Put the data fix in the same task or an earlier wave; otherwise merge-wN goes red.

- Snapshot/"unchanged" specs: before writing "snapshot unchanged" or "queues identical", check the test fixtures for the setting the stage changes. If a fixture sets it, the spec says "regenerate snapshot; every changed line must be the intended one".

- Content-change tasks (re-home, drop, rename ids): the planner adds to Done: "run the project's whole content test suite (its command is in TEAM.md or pipeline.json gates), update every older test whose count or id assumption the change breaks". A task that passes only its own tests goes red at the merge gate.

- Tasks that edit old content lines (tags, text, ids) must name the project's invariant tests and any exemption helper they use in Done (the project lists them in TEAM.md): the helper is part of the task.

- Content or rendering change: every such task names a real-data check in Done (a one-off smoke on the real course, or a content validator rule), and a UI feature ends with a web-tester smoke at 390x844 (`Type: webtest` task writing a report that a script validates: only PASS or FAIL rows, never UNVERIFIED). Give the web-tester 100 turns and only the browser steps; name the exact words or screens to reach, or it reports "not shown". A fix whose file lives in a nested private course repo (workspace/<course>) must be committed in that repo by the task, not left as a working-tree edit. Acceptance commands that run course tests call `bash scripts/course-test.sh <dir>`, never raw `node --test <glob>` (it lacks the kit root variable).
